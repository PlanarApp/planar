## Ветки и main

- В `main` напрямую не мержим и не коммитим: ни `deliver`, ни `merge --into main`, ни локальные коммиты в `main`. Всё попадает в `main` только через MR (GitLab, `glab mr create`), который вливает человек.
- Доставка модуля — в ветку под MR: `.dpcli/dpcli deliver <m> --into mr/<m>` (ветка `mr/<m>` создаётся от `main`), затем по команде пользователя — `git push -u origin mr/<m>` и `glab mr create`. Заголовок и описание MR и коммиты — на языке `language.commits` из `dpcli.yml`.
- Пуш и создание MR — только по команде пользователя. Исключение — задачи Planar (ниже): их сдаём сами.

## Задачи Planar (PLNRAPP)

- «Бери следующие задачи» = задачи Planar проекта PLNRAPP в статусе «К работе» (MCP `search_tasks`, `statusCategory=todo`). Задачи PLNRSAAS не берём.
- Взял задачу → статус «В работе» (`update_task`, statusId `fb58c05b-8e13-4f2a-872a-39d0e309169f`); дальше статус двигает слияние MR (модуль gitlab).
- Готовый план работы → дописать в описание задачи, не затирая исходный текст.
- Задачу вернули → сначала прочитать её комментарии. На назначенный тебе комментарий после исправления — ответить, что сделано, и отметить его готовым.
- Ветка `mr/PLNRAPP-N` от `main`, ключ в заголовке MR. Модуль gitlab берёт ключи из ветки, заголовка и описания MR — чужие ключи в описании закроют чужие задачи. Заголовок MR — `PLNRAPP-N: <суть>`, описание — разделы «что сделано» и «проверка»; язык — по `language.commits` в `dpcli.yml`.
- Доступ к Planar — MCP `planar` (адрес и токен в `~/.claude.json`, в репозиторий не класть). Проверка руками — curl (POST `initialize`, `Accept: application/json, text/event-stream`); urllib из Python получает 403 — это не плохой токен. MCP не отдаёт названия статусов: ID статусов — из `GET /sync/bootstrap?clientId=…` с тем же Bearer-токеном.
- Задача полностью готова → полный `pnpm test` и `pnpm lint` из корня (как в CI) → commit → `git push -u origin mr/PLNRAPP-N` → `glab mr create`.
- Автомерж — только флагом «слить после успешного CI»: дождаться у MR `head_pipeline`, затем `glab api -X PUT projects/planarhq%2Fplanar/merge_requests/N/merge -f merge_when_pipeline_succeeds=true` и проверить, что MR остался open. Не `glab mr merge --auto-merge` — сливает сразу. Новый пуш сбрасывает флаг.
- После слияния — убрать хвосты: локальная ветка `mr/PLNRAPP-N`, копии и ветки dpcli (`.dpcli/dpcli gc --remove`), стенд (`./dev.sh stack <ID> down`), временные файлы.

## Общая рабочая копия и коммиты

- В той же копии работают другие сессии: переключают ветки и держат незакоммиченные правки. Никогда `git add -A` / `commit -a` — только `git commit -- <свои пути>`; перед коммитом проверить `git branch --show-current` и `git status`. Для своей задачи лучше отдельный `git worktree`.
- CI-стадия lint — `pnpm lint` = `eslint . && prettier --check .`; vitest и vue-tsc форматирование не ловят. Перед коммитом — `npx prettier --write <свои файлы>`, перед пушем — `pnpm -s lint` в корне.

## Хост

- Хост общий с чужими проектами: load average 8–24 на 24 ядрах, замеры скорости шумят ±30 мс — перед замерами смотреть `uptime`, чужие контейнеры не трогать.
- Порт 3000 занят чужим caddy: dev-стек вне `./dev.sh stack` — с `API_PORT=3300` (web 5173).
- Тестовая БД `planar-testdb` (порт 55432) — с `fsync=off` (`./dev.sh testdb`): без этого DROP DATABASE под нагрузкой > 60 с, тесты 343 с вместо 47 с, копятся базы `planar_t_*`.
- Диск уже заполнялся на 100%: перед e2e смотреть `df`, убирать свои образы, тома и тестовые базы; `docker builder prune` — только с разрешения пользователя.

## Стенды и e2e

- Каждой задаче — свой стенд: `eval "$(./dev.sh stack <ID>)"` поднимает `planar-<id>` на свободных портах и в своей подсети, с чистой БД и seed, ждёт health и экспортирует `WEB_PORT`, `API_PORT`, `DEV_PG_PORT`, `E2E_BASE_URL`. Снять — `./dev.sh stack <ID> down`.
- Браузерные e2e — только `DEV_STACK=<ID> ./dev.sh e2e-web [файлы]`: каждый прогон идёт на чистой БД.
- Карточки ссылаются на эти строки и не задают порты, подсети и имена compose-проектов сами.

## Малый модуль и контекст главной сессии

- Модуль из 2–3 задач («без координатора») ведёт свежий `dp-coordinator` с `model: sonnet` и без ревьюера, а не главная сессия.
- Главная сессия делает `/clear` после каждой волны задач и после каждой доставки; состояние берётся из журнала.

## Оркестрация агентов

- `.dpcli/dpcli merge <ветка>` без `--into` вливает в `main` — координатор всегда указывает `--into feature/<m>`.
- Общий контракт (например, C-modules) — один владелец; параллельные модули его не версионируют каждый сам.
- Уведомления исполнителей приходят главной сессии, не координатору — пересылать «<ID> reported»; координатор, завершивший ход до исполнителей, — будить.
- Отчёт исполнителя — только `build/dpcli/<ID>.report.json` в своей копии, не общий `/tmp`.
- `dont_touch` проверяется по первому слову пункта: «apps/api/src/ — кроме X» перекрывает X из scope — так не писать.
- Действия, запрещённые исполнителю классификатором (pkill, job start), главная сессия за него не делает.
