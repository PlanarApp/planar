Методика и воспроизведение — `e2e/web/perf/profile/README.md`. Стадии — медианы по прогонам, снятые инструментацией страницы

## mutate (правка названия, Enter → смена текста в DOM): 571 мс → 20 мс

| стадия                                                                                                             |           база, мс | с прототипами, мс |
| ------------------------------------------------------------------------------------------------------------------ | -----------------: | ----------------: |
| Enter → начало транзакции mutate (разбор, zod, чтение в мутаторе)                                                  |                  1 |                 1 |
| транзакция mutate (rw на все таблицы, запись `_queue` в ней же)                                                    |                 13 |                13 |
| liveQuery `useProjectTasks`: перечитать задачи + связи (+ сборка TaskView, group/sort, рендер — в базе неотделимы) |            **557** | 0 (патч в памяти) |
| сборка TaskView, group/sort, рендер → DOM                                                                          | внутри строки выше |                 6 |
| **итого**                                                                                                          |            **571** |            **20** |

Что внутри 557 мс базы (временная шкала одной правки, `results/base2/mutate.json`):

- `tasks` getAll 3334 строк ≈ 75…85 мс;
- `views()` при > 500 задач читает `taskAssignees` (10 000 строк) и `taskLabels` через **`table.filter(...).toArray()` = обход курсором**, ~494 мс на скан
  (сырой IndexedDB: `getAll` всей таблицы 142 мс, курсор 273 мс; поверх курсора Dexie ещё ведёт учёт диапазонов liveQuery на каждую строку:
  `dexie.js:2248` 4,5 с, `continue` 2,3 с, `addRange` 0,26 с на 20 правок). DOM обновляется ровно тогда, когда заканчивается скан `taskAssignees`;
- такой пересчёт происходит **3 раза на одну правку** (локальная транзакция; затем pull после push — rebase откатывает и повторяет очередь, это снова пишет `tasks`;
  затем второй pull) → CPU страницы **≈ 1,37 с на правку** (busy 27,5 с / 20 правок), из них dexie 7,9 с, `(program)` 13,6 с (нативный код вне JS, включая десериализацию результатов IndexedDB; не разделено),
  GC 0,5 с, Vue всего ≈ 0,8 с. На метрику попадает только первый пересчёт, но остальные два блокируют поток после обновления DOM;
- rw-транзакция rebase (`db.transaction('rw', db.tables)`) ждёт окончания читающих сканов (105 → 583 мс в одном прогоне) — всё сериализуется.

Гипотезы координатора:

- «useProjectTasks пересчитывает всё на каждое изменение» — **подтверждено**, главная причина — скан связей курсором, не group/sort (`val()` сортировки — 107 мс на 60 пересчётов за 20 правок).
- «в каждой строке свои liveQuery пикеров» — **для mutate отвергнуто**: при правке задачи транзакций по `statuses/labels/spaceMembers/users` нет (пикеры читают другие таблицы);
  это цена монтирования (≈ 100 мелких транзакций на вход в проект, см. switch), а не правки.
- «mutate пишет `_queue` → liveQuery `_queue`/`syncState`» — подтверждено, но дёшево (< 1 мс каждая; ~7 крошечных транзакций).
- «push → poke → pull → rebase → второй пересчёт» — подтверждено (см. выше, 3 пересчёта).

Правки (эффект измерен на последовательной цепочке сборок, `results/effects.md`):

1. **P1** `tasks/queries.ts`: связи — `table.toArray()` + фильтр в JS вместо `filter().toArray()` (курсор): **571 → 121 мс** (mutate), попутно switch 738 → 262, warm 850 → 526, realtime 1397 → 421, cold 3307 → 3062.
   Одна строка кода; 324 юнит-теста web проходят. Оговорка: часть выигрыша — кэш запросов Dexie 4 (`Cache` middleware: результаты `toArray` связей живут, пока таблица не менялась, +3 с после отписки); у `filter()` этот кэш не работает.
2. **P6** проекция задач проекта в памяти (`useProjectTasks` читает IndexedDB один раз, дальше патчится построчными событиями записи реплики из `DexieTx`/`applyServer`): **121 → 27 мс**.
   Требует правки контракта C-client (новый экспорт событий; инвариант «все записи реплики идут через sync-клиент») — см. «Контракты и архитектура».
3. **P10** `readonly(ref)` в `useQuery`/`useLive` → голый `shallowRef`: `readonly()` глубоко оборачивает каждую из 3334 задач в Proxy (`reactivity get` 277 мс на 20 правок): **26 → 20 мс**, realtime 84 → 67.

Остаток 20 мс: 13 мс транзакция mutate (rw на все таблицы; можно сузить `db.tables` до таблиц мутатора — не пробовалось) + 6 мс патч/сортировка/рендер.

## switch (клик по проекту в боковой панели → строки проекта в DOM): 624 мс → 77 мс (медиана), p95 738 → 98…111

| стадия                                                     | база, мс |                               с прототипами, мс |
| ---------------------------------------------------------- | -------: | ----------------------------------------------: |
| клик → маршрут, монтирование ProjectScreen, старт запросов |       37 |                                              ~0 |
| чтение `tasks` + связей из IndexedDB                       |  **486** | 34 (только первый заход в непрочитанный проект) |
| сборка TaskView, group/sort, Vue-рендер строк → DOM        |      108 |                                              42 |
| **итого, медиана 10**                                      |  **624** |                                          **77** |

Оба проекта по 3333 задач, поэтому «большой» и «малый» переходы в базе одинаковы (≈ 600 мс). CPU базы: 6,5 с / 10 переходов; dexie 1,4 с, Vue runtime-core 0,65 с, reka-ui 0,17 с.
p95 из 10 — это максимум, поэтому **первый заход в ещё не прочитанный проект определяет p95** (в сборках с P6/P7: 453 → 382 → 307 мс первый переход, остальные 70…180).

Гипотеза «холодное чтение 3334 задач и связей + индекс» — **подтверждена** (скан связей курсором, как в mutate). Дополнительно:

- на входе в проект монтируются 27 строк × 4 пикера = **~110 liveQuery/транзакций IndexedDB** (`statuses/labels/spaceMembers/users` на каждый пикер) — после первого рендера, на критический путь не попадают, но грузят поток;
- ~50 мс на переход — монтирование Popover (reka-ui) в каждом пикере каждой строки (рендер 27 строк).

Правки:

1. **P1**: 738 → 262 (p95).
2. **P6+P7** (keep-alive: до 3 проектов остаются в памяти и патчатся событиями) + **P9** (preload проекта из URL до старта приложения, см. warm): повторный переход — только рендер, ~130…150 мс; первый заход в непрочитанный проект остаётся 300…450 мс (чтение без кэша Dexie, пол — 260 мс по `idb-micro`: tasks по индексу 65 + assignees 142 + labels 48).
3. **P11** ленивый Popover в `OptionPicker` (reka-ui монтируется при наведении/фокусе/клике, до этого — лёгкая кнопка с той же разметкой): 130 → 80 мс на повторный переход, warm 475 → 403.
4. **P12** prefetch остальных проектов (до 3) в простое через 500 мс после первого проекта: p95 307 → 104…111 (первый заход тоже из памяти). Компромисс: память и фоновое чтение; на практике — prefetch по `pointerenter` на ссылку проекта.
5. **P4** общие справочники пространства (один liveQuery на (вид, spaceId) вместо ~110): метрики не изменились (±шум), убирает ~100 транзакций на вход в проект — оставлен как гигиена, не как выигрыш.
6. Отвергнуто: **P3** параллельное чтение `tasks`+связей (сырой IndexedDB: 3 таблицы параллельно 318 мс ≈ сумма 375 — выигрыша нет; mutate +10 мс из-за `count()`), **P13** `overscan` 8→3 (warm/switch в шуме, прокрутка не меняется).

## warm (reload при заполненной IndexedDB → первая строка): 850 мс → 380…406 мс

| стадия                                                           | база, мс | с прототипами, мс |
| ---------------------------------------------------------------- | -------: | ----------------: |
| загрузка скриптов и старт приложения (до запроса `/api/auth/me`) |       61 |                64 |
| `/api/auth/me` (router guard ждёт его до первого маршрута)       |       24 |                 9 |
| момент начала чтения задач из IndexedDB (от навигации)           |      142 |       **69** (P9) |
| чтение `tasks` + связей                                          |  **580** |               268 |
| сборка, Vue-рендер → первая строка                               |      128 |                68 |
| **итого, медиана 5**                                             |  **850** |           **406** |

Гипотеза «синхронный bootstrap/pull до первой отрисовки» — **отвергнута**: на тёплом старте `lead()` делает `void kick()`, pull идёт параллельно и первую строку не ждёт
(в таймлайне pull стартует до рендера, но рендер от него не зависит). Что на критическом пути: старт скриптов (61 мс) → `/api/auth/me` (router guard, 24 мс) →
`startSync` (`db.open`, 4 последовательных чтения/записи `_meta`, ~70 мс после открытия) → чтение задач → рендер.
Сырой пол чтения (`idb-micro`): `tasks` по индексу `projectId` 65 мс + `taskAssignees` целиком 142 + `taskLabels` целиком 48 = **≈ 260 мс** — совпадает с 268 в прототипе:
дальше уменьшить можно только объёмом (читаем 10 000 строк `taskAssignees` ради 3333 нужных).

Правки: **P1** 850 → 526; **P9** preload (`main.ts` → `preloadProject(pid)` из URL до `initSession`): чтение стартует на 70 мс раньше (142 → 69 мс от навигации), но в итоге warm выигрывает мало (498 → 488): чтение теперь делит IndexedDB с `startSync` (его `_meta`-запросы ждут большое чтение до 330 мс); **P11** 475 → 403.
Остаток до бюджета — в объёме чтения связей: встроить `assigneeIds`/`labelIds` в строку задачи или добавить `projectId` в строки связей (оценка по `idb-micro`: чтение 65 мс вместо 260 → warm ≈ 210; **не прототипировалось**, нужна правка C-schema).

## cold (пустая IndexedDB → первая строка): 3307 мс → 1690…1840 мс

| стадия                                                         | база, мс | с прототипами, мс |
| -------------------------------------------------------------- | -------: | ----------------: |
| старт приложения, `/api/auth/me` → запрос bootstrap            |      206 |               205 |
| bootstrap: ответ сервера (8,1 МБ JSON, без сжатия)             |      383 |               350 |
| bootstrap: приём тела + `JSON.parse`                           |      145 |               149 |
| zod-разбор `syncBootstrapSchema` до начала записи              |       75 |                77 |
| запись в IndexedDB (одна транзакция, 18 `clear`, 23 368 `put`) | **1721** |               614 |
| чтение проекта, сборка, рендер → первая строка                 |      780 |               400 |
| **итого, медиана 3**                                           | **3307** |          **1795** |

Гипотеза «bootstrap JSON → bulkPut всех сущностей одной транзакцией» — **подтверждена**: запись = 52 % времени. Это не накладные расходы Dexie, а пол IndexedDB:
сырая запись 10 000 строк `tasks` одной транзакцией — **867 мс с 4 индексами** (`parentId, projectId, spaceId, statusId`), 519 мс без индексов (`idb-micro`);
всего строк 23 368 (tasks 10 000 + taskAssignees 10 000 + taskLabels 3334). В CPU страницы: нативный `put` 657 мс + Dexie `proto.<computed>` 233 мс + `(program)` 744 мс;
zod 88 мс; Vue — мелочь. Сервер (CR-9, `pnpm --filter @planar/e2e measure`): `bootstrap_ms=378`, `pull_ms=15`, `push_ms_p95=24`, `poke_ms_p95=50`. Ответ не сжимается:
gzip → 0,72 МБ (в 11 раз), на localhost это ничего не даёт, на реальной сети 8 МБ — отдельная проблема.

Правки:

1. **P8** bootstrap пишет сначала открытый проект (по `location`, транзакция с очисткой, 7813 строк), остальные `tasks`/связи — пачками по 1000 отдельными транзакциями с отдачей потока между пачками, курсор — после последней:
   **запись 1721 → 614 мс, cold 2877 → 1686**. Бюджет 2000 выполняется. Риски — в «Допущениях».
2. Не прототипировалось, оценки: строить состояние открытого проекта прямо из payload bootstrap (минуя перечитывание после коммита): −200 мс; отложенные пачки не вызывают повторного `reset` (сейчас вызывают: лишнее чтение 240 мс после первой строки);
   сжатие ответа (C-http/прокси); постраничный bootstrap по проекту (C-sync); убрать индексы `spaceId`/`parentId`, если они не нужны запросам (−330 мс на 10 000 задач по `idb-micro` без индексов — нужен аудит запросов).

## realtime (правка у A → текст у B, `Date.now` на одной машине): 1398 мс → 64 мс (медиана), p95 1546 → 65…99

| стадия                                                         | база, мс | с прототипами, мс |
| -------------------------------------------------------------- | -------: | ----------------: |
| A: Enter → отправка push                                       |  **673** |                24 |
| push → сервер → poke у B                                       |       41 |                20 |
| B: pull (запрос + разбор)                                      |       11 |                11 |
| B: rebase-транзакция, пересчёт `useProjectTasks`, рендер → DOM |  **641** |                 8 |
| **итого, медиана 10**                                          | **1398** |            **64** |

Гипотеза «poke → pull → applyServer → liveQuery → DOM» подтверждена, но **серверная часть мала** (push 24 / poke ≤ 50 / pull 11–15 мс по CR-9 и по таймлайну). Две клиентские причины по ~650 мс:

1. **A** — `cycle()` сначала делает `pull()` и только потом `push()`: к моменту push на A идёт пересчёт после локальной правки (скан связей) и rw-транзакция pull (ждёт сканы), push уходит через 673 мс.
   **P2**: порядок `push` → один `pull` (C-sync: push не зависит от курсора): **−130 мс на realtime** (421 → 293 при уже исправленном скане), mutate не меняется.
2. **B** — те же пересчёт и скан связей при получении изменения (641 мс); лечится P1/P6.

Выбросы в сборках с прототипами (296…956 мс, 1–2 из 10) — ответ `POST /sync/push` занимает 300…950 мс (`results/P12test/realtime.json`, прогон 0: push 297 мс при клиентской части ≈ 20 мс), то есть серверная задержка push, не клиент. Её разбор — в серверной задаче (CR-9 даёт `push_ms_p95=24` в тихом стеке).

Не прототипировано, но следует из замеров (для задачи оптимизации):

- встроить `assigneeIds`/`labelIds` в строку задачи (или `projectId` в строки связей): чтение проекта 260 → 65 мс (warm ≈ 210, первый заход в проект ≈ 100 мс вместо 300…450) — **C-schema/C-sync/C-mutators**;

- сузить `db.transaction('rw', db.tables, …)` в `mutate`/`applyServer` до нужных таблиц: сейчас rw-транзакция на все таблицы ждёт любых читателей.

## Допущения и границы

- Chromium headless (Playwright 1.60), одна машина (24 ядра), стек и браузер на localhost, без троттлинга CPU/сети; цифры — относительные. Сеть не моделируется (на реальной сети bootstrap 8 МБ добавит секунды).
- Число задач фиксировано (10 000, 3 проекта); линейность по объёму не проверялась. P1 читает таблицы связей целиком — при тысячах проектов и малом открытом проекте это хуже, чем `anyOf`; нужно ветвление или встраивание связей.
- Кэш запросов Dexie 4 искажает «переключение туда-обратно» в пользу повторного чтения; «пол без кэша» — 260 мс (`idb-micro`).
- P6/P7: кросс-вкладочные изменения не видны (события только в той вкладке, где идёт запись; нужна пересылка событий через BroadcastChannel или контрольный liveQuery); порядок событий от конкурентных транзакций mutate/applyServer не доказан формально (прогоны 20×3 правок и realtime расхождений не показали); 16 юнит-тестов красные, потому что пишут в `db` напрямую.
- P8: пока идёт фоновая запись, проекты кроме открытого неполные; курсор ставится в конце, оборванный bootstrap повторяется; интерфейс не знает о «неполной реплике».
- P11: подмена кнопки на Popover при фокусе клавиатурой — грубо (фокус возвращается эвристикой), доступность не проверялась.
