# Модуль web (WB)

## 1. Цель
Фронтенд Planar в `apps/web`: SPA на Vue 3 + Vite, ставится как PWA, раскладки для desktop и mobile, мгновенный интерфейс на локальной реплике. Бюджеты скорости — `docs/roadmap.md` §7; это условия приёмки, а не пожелания.

## 2. Решения пользователя
- Vue 3 + Vite, SPA + PWA; синхронизация — вариант B (`docs/roadmap.md` §1, §3).
- Простота: не перегружать интерфейс. Каждый экран делает одну вещь, вторичное — в меню и Cmd+K.
- Один workspace; вход только по логину и паролю.
- В `main` ничего не сливаем без одобрения пользователя.

## 3. Контракты
- **Потребляем** из `docs/contracts/core.md`: C-sync, C-mutators, C-modules, C-http. Они в ветке `feature/core`; свежие правки забираем слиянием `feature/core` в `feature/web` в копии модуля (`git merge feature/core`). В `main` не вливаем.
- **Владеем** C-ui, пишем его до WB-1:
  - дизайн-токены как CSS-переменные для светлой и тёмной темы;
  - шкала отступов и шрифтов;
  - брейкпоинт mobile < 768px;
  - базовые компоненты (Button, Input, Select, Popover, Dialog, Menu, Avatar, Badge, Tooltip) на Reka UI + Tailwind 4;
  - правила иконок: один набор, `lucide-vue-next`;
  - контракт точек расширения фронта (C-modules, сторона web): `routes`, `views`, `taskPanels`, `commands`, `fieldTypes`, `settings`.
- Протокол синхронизации меняет только core, через шлюз. Нашли расхождение — сообщаем `<ID> contract: …`.

## 4. Правила среды
- Код — только `apps/web/**` (и `e2e/web/**` для UI-сценариев). Общие мутаторы в `packages/shared` не правим: это core. Не хватает мутатора — `contract:`.
- Компоненты: Vue SFC `<script setup lang="ts">`; состояние данных — реплика Dexie через `useQuery()`; состояние интерфейса — composables (без Pinia, пока не понадобится).
- Тесты: Vitest + `@vue/test-utils` (happy-dom), клиент синхронизации — против in-memory сервера по C-sync из `packages/shared` (если его нет — WB-2 пишет фейк у себя в `apps/web/src/sync/__tests__`).
- Сборка: `pnpm --filter web build`. Размер начального бандла проверяется скриптом `apps/web/scripts/size.mjs`: gzip начальных чанков ≤ 200 КБ, иначе FAIL. Скрипт добавляет WB-1, он входит в проверку каждой задачи.
- Строки интерфейса — только через i18n (ru, en).
- Доступность: кнопки и поля с подписями, фокус виден, всё управляется клавиатурой.

## 5. Задачи
Оценки и зависимости — `docs/roadmap.md` §5.2.

### WB-1 Каркас приложения
- **Состав:**
  - Vite + Vue + router + Tailwind 4 + Reka UI, токены и компоненты C-ui;
  - раскладка: боковая панель (пространства → проекты, избранное, Inbox, «Мои задачи»), верхняя панель, контент; на mobile — нижняя навигация и экраны вместо панелей;
  - тёмная тема (системная и ручная), i18n;
  - PWA через vite-plugin-pwa: manifest, иконки, service worker, предложение установить, офлайн-оболочка;
  - скрипт размера бандла.
- **Приёмка:** build проходит; бюджет размера выполняется; Lighthouse PWA installable (или проверка manifest и SW скриптом); тесты раскладки на двух ширинах.

### WB-2 Клиент синхронизации
- **Состав:**
  - `apps/web/src/sync/`: Dexie-схема по C-schema;
  - bootstrap; pull по курсору; push-очередь мутаций в IndexedDB (переживает перезагрузку);
  - rebase: после pull применяем серверное состояние, затем заново неподтверждённые мутации;
  - WS с переподключением (экспоненциальная задержка), poke → pull; `reset` → bootstrap;
  - `useQuery(fn)` — реактивный запрос к реплике (liveQuery → ref);
  - `mutate(name, args)` — оптимистичное применение через общий мутатор и клиентский `Tx`;
  - вкладки браузера: одна ведёт WS, остальные получают изменения через BroadcastChannel (или каждая держит свой WS — выбрать проще и обосновать).
- **Приёмка (тесты):** оптимистичное применение; подтверждение; откат отклонённой мутации; офлайн-очередь переживает перезапуск; rebase при конкурентной правке; `reset`; на 10 000 задач bootstrap ≤ 2 с, локальная мутация ≤ 50 мс (замер в тесте, числа в отчёте).

### WB-3 Вход и пользователи
- Экраны: первичная настройка (если пользователей нет), вход, профиль (имя, аватар, пароль, тема, язык); админ — список пользователей, создание, роль, блокировка. Работает по C-http.

### WB-4 Вид «Список»
- Виртуализация (TanStack Virtual), группировка по статусу, исполнителю, приоритету или метке; сортировка; инлайн-правка названия, статуса, исполнителя, срока, приоритета; быстрое создание строкой внизу группы; множественный выбор (Shift/Cmd), массовые действия; клавиатура j/k, Enter, x.
- **Приёмка:** 10 000 задач прокручиваются без подвисаний (замер кадров в тесте Playwright), переключение проекта ≤ 100 мс.

### WB-5 Вид «Доска»
- Колонки по полю группировки, перетаскивание между колонками и внутри (rank), сворачивание колонок, лимит карточек на экране с виртуализацией; на mobile — горизонтальный свайп колонок.

### WB-6 Карточка задачи
- Боковая панель на desktop и страница на mobile/по прямой ссылке `/t/PLN-123`. Поля; описание в TipTap (Markdown-ввод, упоминания, вставка изображений через `/files`); подзадачи; чек-лист; вложения; лента «комментарии + активность» с @упоминаниями и реакциями; наблюдатели. Точка расширения `taskPanels`.

### WB-7 Cmd+K, клавиатура, поиск
- Палитра: переходы, создание задачи, действия над выбранными, команды модулей. Горячие клавиши (`?` — шпаргалка). Поиск по реплике — по названию, ID и описанию; результаты ≤ 50 мс на 10 000 задач. Шорткат: только локальный поиск; серверный FTS, когда реплика перестанет помещаться.

### WB-8 Сохранённые виды
- Конструктор фильтров (поле, оператор, значение; И/ИЛИ на одном уровне), группировка, сортировка, видимые поля; личные и общие виды; вид хранится в сущности `saved_views`.

### WB-9 Inbox и «Мои задачи»
- Inbox по сущности `notifications`: прочитано, отложить, перейти. «Мои задачи»: назначенные мне, по срокам. Колокольчик со счётчиком. Включение push: запрос разрешения, подписка, проверка на iOS (подсказка «установите приложение»).

### WB-10 Настройки
- Пространства (приватность, участники), проекты (префикс ID), статусы с категориями (порядок перетаскиванием), метки, модули (включить и выключить по C-modules).

### WB-11 API-токены (после CR-10, этап после MVP)
- Профиль → «API-токены»: выпуск (название, права, срок), однократный показ с копированием, список, отзыв, инструкция подключения MCP (URL `/mcp` и пример конфига клиента).

## 6. Волны
- WB-1 ‖ WB-2 → WB-3 → WB-4 ‖ WB-5 ‖ WB-6 → WB-7 ‖ WB-8 ‖ WB-9 ‖ WB-10 → шлюз MVP → WB-11.
- Не больше 4 исполнителей одновременно.
- Зависимости от core (CR-3, CR-5, CR-6, CR-7, CR-8): задача стартует, когда нужная задача core принята в `feature/core` и влита сюда; до этого — только по контракту с фейком, если это не удлиняет работу.
- Перед шлюзом MVP — e2e UI-сценарии в `e2e/web/`: вход, создать задачу, перетащить, комментарий и упоминание доходят до второго пользователя, офлайн-правка.
- **WB-2: замер mutate на fake-indexeddb (66–75 мс; голый put в tasks с 4 индексами 35–55 мс) не отражает IndexedDB браузера. В WB-2 порог на fake-indexeddb — ≤100 мс как защита от регрессий; бюджет §7 (≤50 мс, bootstrap ≤2 с) проверяется в настоящем Chromium (Playwright) e2e-замером web перед шлюзом MVP и в CR-9; не выполнен там после 2 попыток — шлюз** (2026-10-22) — fake-indexeddb — JS-эмуляция, стоимость индексов несопоставима с B-деревом браузера; бюджет не ослабляется, меняется только место замера
