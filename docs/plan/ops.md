# Модуль ops (OP)

## 1. Цель
Planar можно развернуть на сервере одной инструкцией, сохранить данные и восстановить их, наблюдать работу и обновлять без потери данных. Стек — `docs/roadmap.md` §2 и §2.6: Docker Compose, Postgres 18, Caddy, файлы в папке. Без Kubernetes, S3 и внешних SaaS.

## 2. Решения пользователя
- Простота во всём. Файлы — просто в папку. Один VPS (2026-10-22).
- Продолжать по плану (2026-10-25).
- В `main` — только с одобрения пользователя.

## 3. Контракты (`docs/contracts/ops.md`)
- Переменные окружения prod (полный список с назначением и значениями по умолчанию).
- Тома и каталоги данных.
- Формат бэкапа и его версия.
- Эндпоинты `/api/health` (живость и готовность) и `/api/metrics`.

Правки C-http (новые эндпоинты) — строкой `contract: …` главной.

## 4. Задачи
- **OP-1 prod-стек целиком.**
  - `compose.yml`: postgres (том), api (собранный образ, без исходников), caddy (автоматический TLS по `PLANAR_DOMAIN`; без домена — `:80` и самоподписанный).
  - Порт api наружу не публикуется. `TRUST_PROXY` — подсеть Caddy. Заголовки безопасности в Caddy: HSTS, CSP по C-http, X-Content-Type-Options, Referrer-Policy.
  - `./dev.sh prod-smoke` (есть из WK-7c) доводится: поднимает prod-стек под своим `COMPOSE_PROJECT_NAME` на свободных портах, проверяет health, вход, создание задачи, WS, `/collab`, `/f/*`, загрузку файла, затем down.
  - Образ api — многостадийная сборка, запуск не от root, размер в отчёте.
- **OP-2 Бэкапы и восстановление.**
  - `./ops/backup.sh`: `pg_dump -Fc` и архив каталога файлов (контентно-адресуемые файлы — rsync или tar), атомарно, с датой; ротация (7 дневных, 4 недельных) и проверка целостности.
  - `./ops/restore.sh <архив>`: на чистый стек.
  - Тест: стек → данные → бэкап → снос томов → restore → те же данные (число задач, файлы по sha256, вход).
  - Расписание: systemd timer или cron, пример в инструкции.
- **OP-3 Наблюдаемость.**
  - `/api/health`: живость. `/api/health/ready`: БД, миграции, pg-boss.
  - `/api/metrics` в формате Prometheus: запросы, задержки, WS-подключения, очередь pg-boss, размер БД. Доступ — токеном или только из внутренней сети.
  - Логи pino в JSON, ротация docker (`max-size`).
  - Без собственного Grafana-стека: в инструкции — как подключить внешний.
- **OP-4 Обновления.**
  - `./ops/upgrade.sh`: бэкап → pull или build → миграции (идемпотентные, до переключения) → перезапуск api → health → откат образа при провале health.
  - Совместимость миграций: только расширяющие изменения в одном релизе (правило в инструкции).
- **OP-5 Инструкция** `docs/guides/deploy.md` (`dp-writer`).
  - Требования к серверу.
  - DNS и домен.
  - `.env` с генерацией секретов (`PLANAR_SECRET_KEY`, VAPID).
  - Первый запуск и создание владельца.
  - Бэкапы и восстановление, обновление, мониторинг.
  - Что делать при проблемах.
  - Команды проверены на OP-1…OP-4.

## 5. Волны
OP-1 → OP-2 ‖ OP-3 ‖ OP-4 → OP-5. Не больше 4 исполнителей.

## 6. Правила среды
- Как в `docs/plan/core.md` §4. Отчёт — только `build/dpcli/<ID>.report.json` в своей копии.
- Слияние — только `.dpcli/dpcli merge <ветка> --into feature/ops`.
- **Стек проверки пользователя (`planar-dev`, порты 3300 и 5173, туннель) не трогать.** Prod-стек — своё имя проекта (не `planar`, оно в `compose.yml`, задавать через `-p planar-<ID>`) и свои порты. Порты 80 и 443 на хосте заняты чужим прокси — prod-smoke на свободных портах.
- Диск: после тестов удалять свои образы, тома и архивы бэкапов.
- Шлюзы — сразу одной строкой главной.
