# Модуль p4 (PF)

## 1. Цель
Остатки исходного списка функций (`docs/roadmap.md` §12). Каждая функция — модуль `modules/<id>` по C-modules, включается и выключается. Интерфейс — на C-ui v4 (`docs/contracts/design.md`).

## 2. Решения пользователя
- Продолжать по плану (2026-10-25). Объём — §12 роадмапа.
- ИИ не делаем. Интеграция с кодом — только GitLab (уже есть).
- В `main` — только с одобрения пользователя.

## 3. Контракты (`docs/contracts/p4.md`, до первого исполнителя)
- Сущности и мутаторы модулей recurring, templates, goals, email, plugins.
- Протокол внешних плагинов (`postMessage`).
- **Владелец C-\*** — главная. Правки — строкой `contract: …` главной, номер версии выставляет главная (сейчас C-schema 9, C-sync 2, C-mutators 4, C-modules 10, C-http 11).

## 4. Задачи
- **PF-1 Повторяющиеся задачи** (`modules/recurring`).
  - Правило на задаче: каждый N дней, недель или месяцев, по дням недели, «после завершения».
  - Следующий экземпляр создаёт pg-boss cron от имени системного пользователя: копируются поля, исполнители, метки и чек-лист, сроки сдвигаются.
  - Ровно один экземпляр на период, без дублей при повторном запуске. Часовой пояс — проекта.
  - Интерфейс: блок «Повтор» в карточке задачи.
- **PF-2 Шаблоны** (`modules/templates`).
  - Шаблон задачи: поля, описание, чек-лист, подзадачи.
  - Шаблон проекта: статусы, метки, пользовательские поля, набор задач.
  - Задача из шаблона: Cmd+K и меню «Новая задача». Проект из шаблона — в настройках.
  - Сохранить задачу или проект как шаблон.
- **PF-3 Цели и вехи** (`modules/goals`).
  - Веха проекта: дата, задачи; прогресс по категориям статусов.
  - Цель пространства: ключевые результаты — число (ручное) или «задачи, закрытые по фильтру F-filter».
  - Экраны: «Цели» в разделах; вехи на Timeline — вертикальная линия, если модуль timeline включён.
- **PF-4 Email** (`modules/email`).
  - SMTP через nodemailer. Настройки: хост, порт, логин, пароль (шифруется как токен GitLab, `PLANAR_SECRET_KEY`), отправитель.
  - Письма: по уведомлениям (упоминание, назначение) с задержкой 10 мин (не слать, если уже прочитано в приложении) и ежедневный дайджест.
  - Подписка и отписка в профиле; ссылка отписки в письме (подписанный токен).
  - Без настроек SMTP модуль недоступен для включения.
  - Шаблоны писем: текст и простой HTML.
  - Приёмка — против тестового SMTP в тесте (smtp-server в devDeps или своя заглушка).
- **PF-5 Внешние плагины через iframe** (`modules/plugins`, третий уровень §2.5 роадмапа).
  - Админ регистрирует плагин: URL, права (`read` и `write` по сущностям), точки (`taskPanels`, страница в разделах).
  - Плагин работает в `<iframe sandbox="allow-scripts allow-forms">` на своём origin. С приложением общается только через `postMessage` по протоколу из контракта: `init {user, context}`, `query`, `mutate` (через мутаторы и права плагина), `navigate`, `resize`.
  - Origin плагина проверяется на каждом сообщении. Токен плагина ограничен правами.
  - **Безопасность:**
    - нет `allow-same-origin` вместе с `allow-scripts` для того же origin;
    - CSP `frame-src` — только зарегистрированные URL;
    - тесты на отказ при чужом origin и превышении прав.
  - Пример плагина в `examples/plugin-hello/`: статическая страница.
  - Ревью `dp-reviewer` обязательно.
- **PF-6 e2e фазы 4.** По сценарию на функцию (`e2e/web/p4.spec.ts`) и замер §7.

## 5. Волны
PF-1 ‖ PF-2 ‖ PF-3 ‖ PF-4 → PF-5 → PF-6. Не больше 4 исполнителей.

## 6. Правила среды
- Как в `docs/plan/core.md` §4 и `docs/plan/web.md` §4. Отчёт — только `build/dpcli/<ID>.report.json` в своей копии.
- Слияние — только `.dpcli/dpcli merge <ветка> --into feature/p4`.
- **Стек проверки пользователя не трогать.** Это `planar-dev` на портах 3300 и 5173, к нему подключён публичный туннель. `compose.dev.yml` по умолчанию берёт имя `planar-dev`, поэтому `./dev.sh up/down/reset` запускать только с `COMPOSE_PROJECT_NAME=planar-<ID>` и своими `API_PORT`, `WEB_PORT`, `DEV_PG_PORT`. Порт 3000 занят на хосте.
- Шлюзы (`decide --ask`) — сразу одной строкой главной.
