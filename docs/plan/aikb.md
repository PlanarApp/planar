# Модуль aikb — знания ИИ о самом Planar

## 1. Цель
PLNRAPP-233. ИИ не знает устройство Planar: например, не может дать ссылку на задачу, документ или чат — инструменты отдают только id и ключи. Нужно собрать знания по коду и подключить их ко всем ИИ-взаимодействиям: прогоны по задачам (llm и runtime agent), чат (личный и групповой), комментарии к страницам документов (PLNRAPP-219; «Разговор с документом» удалён).

## 2. Решения пользователя (2026-11-16)
- **Только в коде.** Не в документе пакета harness и не в docs-site. Компактный общий блок — в промпте каждого ИИ-прогона; подробности — тоже в коде, ИИ получает их по запросу инструментом (раздел за разделом), чтобы не раздувать контекст.
- Адрес инстанса не зашивать (`poprygun.planarhq.com` — лишь один контур): ссылки собираются из публичного адреса инстанса из окружения (найти существующую переменную — та, что уже используется в письмах и ссылках уведомлений; новую не заводить, если есть).
- Исполнитель — эта сессия модулем dpcli; ИИ Planar снят с исполнителей 233.

## 3. Задачи (подзадачи Planar)
Разбивку на карточки и волны делает координатор по коду.
- **PLNRAPP-234** — шаблоны URL фронтенда по `apps/web/src/router.ts` (и маршрутам модулей): задача по ключу, документ, личный чат, чат задачи и документа, проект, пространство, разделы (доска, список, документы, циклы, «Задачи ИИ», настройки), комментарий (`?comment=<id>` у задачи и страницы). Функция сборки URL в коде + тест, что каждый шаблон соответствует существующему маршруту роутера (тест ломается, если маршрут переименовали). Проверка на реальных страницах — e2e на локальном стенде (`./dev.sh stack`, `./dev.sh e2e-web`): открыть по собранному URL задачу и документ.
- **PLNRAPP-235** — сущности и связи (пространство, проект, задача, статусы и категории, метки, поля, комментарии, циклы, документы, автоматизации, прогоны ИИ): компактно, ключевые id и связи.
- **PLNRAPP-236** — MCP инстанса: список инструментов (генерировать из реестра `apps/api/src/mcp/tools.ts`, а не руками — чтобы не устаревал), входы и права; как агент в runner'е обращается к MCP локально (как это устроено сейчас — по коду ai-runner и agent.ts), когда MCP, когда API.
- **PLNRAPP-237** — ИИ-прогоны: пакеты harness, действия, правила автоматизаций, поля результата (`resultSchema` в `modules/ai/api/run.ts` — тоже по возможности из схемы), подтверждение «да».
- **PLNRAPP-238** — права и ограничения: с чьими правами выполняются инструменты, что запрещено, что требует «да».
- **PLNRAPP-239** — компоновка: общий блок (шаблоны URL с адресом инстанса, правило «на просьбу дать ссылку — готовый URL по шаблону, а не id», сущности в двух-трёх строках, как получить подробности) и инструмент подробностей по разделам. Оценить объём общего блока в токенах и записать в контракт; ориентир — не больше ~1,5 тыс. токенов. Инструмент подробностей — в реестре MCP, по правилу паритета REST ↔ MCP (`PARITY`, тест).
- **PLNRAPP-240** — подключение блока во все прогоны (llm по задаче, agent, чат, комментарии страницы) с тестом на каждый путь; тест, что в чате ответ со ссылкой собирается по шаблону (на заглушке модели). Живую проверку на контуре делает главная сессия после слияния.
- Контракт (`docs/contracts/*`), CHANGELOG. Демо-сид не нужен.

## 4. Приёмка волн и доставка
- После влития каждой волны в `feature/aikb` — проверки как в CI на ветке модуля: `pnpm --filter "@planar/api..." --filter "@planar/ai-runner" build` и `pnpm -s lint`; красное исправлять в этой волне. Новая зависимость — в scope карточки вместе с `package.json` и `pnpm-lock.yaml`.
- Перед deliver: полный `pnpm test`; `git fetch origin main` — если main ушёл вперёд, обновить `mr/PLNRAPP-233` и `.dpcli/dpcli sync aikb`; `.dpcli/dpcli deliver aikb --into mr/PLNRAPP-233`; `aikb done`. Пуш и MR делает главная сессия.

## 5. Условия остановки
- Общий блок не укладывается в ~1,5 тыс. токенов без потери шаблонов URL — вопрос пользователю.
- Для локального доступа агента к MCP нужна правка runner'а или сети (compose, squid) — вопрос пользователю.

## Решения пользователя

- **Цель модуля — собственный ИИ полностью управляет своим инстансом Planar через свой MCP. Знания (общий блок + инструмент подробностей) обязаны покрыть: весь реестр MCP — каждый инструмент, его аргументы, фильтры и права (генерировать из реестра и zod-схем, не руками); структуру данных и связи; harness-пакеты, действия (actions) и события, правила автоматизаций — все триггеры, условия, фильтры и действия (из modules/automations/shared); поля результата прогона; виды и фильтры задач (search_tasks, сохранённые виды); настройки проекта и модулей; рецепты типовых задач управления (завести статус/поле/метку, правило автоматизации, привязать действие пакета к событию, пачечно изменить задачи, найти по фильтрам) с последовательностью вызовов инструментов. Тест: каждый инструмент реестра и каждый тип триггера/действия автоматизаций упомянут в знаниях — новый без описания ломает тест.** (2026-11-16) — уточнение пользователя 2026-11-16: «нужно, чтобы собственный ИИ умел полностью управлять собственным инстансом Planar»
