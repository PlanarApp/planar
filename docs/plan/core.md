# Модуль core (CR)

## 1. Цель
Бэкенд Planar и общий пакет `packages/shared`: каркас монорепо, локальный стек в docker compose, схема БД, синхронизация в стиле Linear, общие мутаторы домена, авторизация, файлы, уведомления и push, модульная система, API-токены, REST и MCP. Общая картина и бюджеты — `docs/roadmap.md` §2–§7.

## 2. Решения пользователя
- Стек — `docs/roadmap.md` §2. Postgres 18 и только он: очереди (pg-boss), pub/sub (LISTEN/NOTIFY), без Redis. ORM — Drizzle.
- Авторизация только по логину и паролю. Workspace один.
- Синхронизация — вариант B (`docs/roadmap.md` §3).
- API-токены пользователя и MCP-сервер входят в ярус A.
- В `main` ничего не сливаем без одобрения пользователя.

## 3. Контракты (координатор пишет до CR-1, файл `docs/contracts/core.md`)
Нужны C-schema, C-sync, C-mutators, C-modules, C-http (`docs/roadmap.md` §4). Модуль `web` потребляет их напрямую, поэтому они должны быть точными. Обязательные пункты:

- **C-sync:**
  - `GET /sync/bootstrap` → `{cursor, lastMutationId, data:{<entity>:[rows]}}`.
  - `GET /sync/pull?cursor=N` → `{cursor, lastMutationId, changes:[{seq, entity, id, op:'put'|'del', data?}], reset?:true}`. `reset` означает «сделай bootstrap заново»: курсор устарел или изменилось членство.
  - `POST /sync/push {clientId, mutations:[{id, name, args}]}` → `{results:[{id, ok, code?}]}`. Мутации выполняются по порядку, каждая в своей транзакции. Идемпотентность — по `client_mutations(client_id, last_mutation_id)`. Отклонённая мутация засчитывается как обработанная.
  - WS `/ws` с авторизацией по cookie. Сервер шлёт `{t:'poke', seq}`, клиент отвечает `{t:'hello', cursor}`.
  - Видимость строки `changes`: пользователь состоит в `space_id` или `user_id` равен ему (личные сущности: уведомления, подписки).
  - `NOTIFY planar_changes, '<seq>'`: только номер, данные в уведомление не кладём.
- **C-mutators:**
  - Регистрация: `defineMutator({name, args: zod, run(tx, args, ctx)})`, где `ctx = {userId, now, server: boolean}`.
  - `Tx`: `get(entity, id)`, `put(entity, row)`, `patch(entity, id, partial)`, `del(entity, id)`, `scan(entity, {index?, eq?})`.
  - Серверная реализация `Tx` проверяет права на каждой записи (членство в пространстве, роль), пишет строку в `changes`, а для задач — activity с изменёнными полями.
  - ID создаёт клиент (uuidv7). Порядок элементов — fractional index в поле `rank`.
- **C-schema:**
  - snake_case в БД, camelCase в TS (Drizzle `casing`).
  - У каждой синхронизируемой строки есть `space_id`: для задач, комментариев и вложений он денормализован, чтобы фильтр работал без join.
  - Пользовательские поля — `tasks.fields jsonb` (заготовка под FT-1).
- **C-modules:** манифест (`docs/roadmap.md` §4). Модуль можно включать и выключать. Выключенный модуль не регистрирует маршруты и мутаторы, а его сущности не попадают в bootstrap.
- **C-http:**
  - Ошибки — `{code, message, details?}`.
  - Сессия — cookie `planar_sid` (httpOnly, SameSite=Lax). Для небезопасных методов проверяется Origin.
  - Bearer-токен (CR-10) ведёт к тому же `ctx.userId`.

У каждого контракта — версия и контрактный тест. Тест ломается, если формат поменяли без правки контракта.

## 4. Правила среды (для всех карточек)
- Node 24, pnpm (lockfile коммитится), TypeScript strict. Зависимости — только из `docs/roadmap.md` §2. Новая зависимость — шлюз, кроме мелких (≤ 1 пакет, без нативного кода, явно нужен задаче): про них пишем в отчёте.
- Тесты — Vitest на реальном Postgres. Исполнители работают параллельно в разных копиях, поэтому:
  - тестовая БД — общий контейнер `planar-testdb` (фиксированное имя, порт 55432, поднимается идемпотентно командой `./dev.sh testdb`);
  - каждый прогон создаёт свою базу `planar_t_<random>`, применяет миграции и удаляет её в конце;
  - dev-стек (`./dev.sh up`) в карточках не нужен.
- `dpcli.yml` `checks.tests` настраивается в CR-1: команда Vitest с фильтром `-t`. Нужен разбор итога в `tests_summary` или гарантия, что 0 найденных тестов даёт FAIL. Координатор проверяет это на CR-1.
- Фронтенд-код (`apps/web`) — зона модуля `web`. В core его не трогаем, кроме заглушки в CR-1.

## 5. Задачи
Оценки и зависимости — в `docs/roadmap.md` §5.1. Ниже — что сверх роадмапа.

### CR-1 Каркас
- **Состав:** pnpm workspace (`apps/api`, `apps/web` — пустая заглушка Vite + Vue, `packages/shared`, `modules/`); `tsconfig.base.json`; ESLint и Prettier; корневая конфигурация Vitest на проекты.
- **Compose:**
  - `compose.dev.yml`: `postgres` (`pgvector/pgvector:pg18`), `api` (watch, bind mount), `web` (vite dev);
  - `compose.yml` (prod): `postgres`, `api`, `caddy` (статика web, проксирование `/api`, `/sync`, `/ws`, `/mcp`, `/files`).
- **`dev.sh`:** `up | down | reset | seed | logs | test | testdb`. `.env.example`.
- **API:** Nest + Fastify, `GET /api/health` (проверяет и БД), логи через pino.
- **Приёмка:**
  - `./dev.sh testdb`, затем `pnpm test` — зелёный;
  - `docker compose -f compose.dev.yml config` и `docker compose config` без ошибок;
  - `./dev.sh up` — health отвечает 200 (проверка с таймаутом); `./dev.sh down`;
  - `pnpm -r build` проходит.

### CR-2 Схема
- **Состав:** все таблицы C-schema, миграции drizzle-kit, сид (пользователь `admin`/`admin` только для dev, 2 пространства, проекты, статусы, метки). `dev.sh seed --tasks N`.
- **Приёмка:** миграции применяются на чистую базу; сид на 10 000 задач укладывается в порог (координатор ставит его по первому замеру).

### CR-3 Авторизация
- **Состав:**
  - argon2id; сессии в БД со скользящим сроком;
  - `POST /api/auth/login`, `logout`, `GET /api/auth/me`;
  - `POST /api/auth/setup` — только пока в системе нет ни одного пользователя (первый становится владельцем);
  - админ создаёт пользователей, меняет роль, блокирует;
  - ограничение частоты попыток входа (таблица в Postgres).
- **Приёмка:** тесты на вход и выход, неверный пароль, повторный setup (отказ), блокировку пользователя, права ролей.

### CR-4 Сервер синхронизации
- **Состав:** по C-sync. LISTEN — одно соединение на процесс, рассылка подключённым сокетам. Реализация `Tx` для сервера.
- **Приёмка:**
  - push → pull у второго клиента;
  - повтор той же мутации не применяется дважды;
  - участник не видит строки чужого приватного пространства (pull, bootstrap, WS);
  - изменение членства даёт `reset`;
  - poke приходит ≤ 500 мс на локальном стеке (замер в тесте).

### CR-5 Мутаторы домена
- **Состав:** в `packages/shared/src/mutators`, код общий для клиента и сервера, без Node API. Пространства, проекты, статусы (категории backlog, todo, in_progress, done, cancelled), задачи (с подзадачами через `parent_id`, ID вида `PLN-123`: префикс проекта и счётчик — на сервере, у клиента временный), исполнители, наблюдатели, метки, чек-лист, комментарии (упоминания `@user` разбираются в массив `mentions`), порядок через `rank`.
- **Приёмка:** юнит-тесты на in-memory `Tx` (его реализация входит в задачу и потом нужна web для тестов) и интеграционные тесты через серверный `Tx`.

### CR-6 Файлы
- **Состав:**
  - `POST /files` (поток, sha256 на лету, лимит из env), `GET /files/:id` (права через пространство вложения), превью для изображений через sharp;
  - хранение `data/files/ab/cd/<sha256>`, одинаковые файлы — один раз;
  - отдача потоком из Nest. Шорткат: без X-Accel; при росте нагрузки переносим отдачу в Caddy.
- **Приёмка:** загрузка, скачивание, отказ без прав, дедупликация, лимит размера.

### CR-7 Уведомления и push
- **Состав:** серверные хуки после мутаций — назначение, упоминание, комментарий или смена статуса в задаче, за которой следишь. Сущность `notifications` (личная, через синхронизацию). Отправка push через pg-boss и `web-push`, ключи VAPID из env (`dev.sh` генерирует их, если ключей нет). Подписки — `POST /api/push/subscribe`. Подписки, на которые сервер push ответил 410, удаляются.
- **Приёмка:** уведомления создаются по каждому триггеру, автор не уведомляет сам себя, задача отправки ставится в очередь (отправка мокается).

### CR-8 Модульная система
- **Состав:** загрузчик манифестов из `modules/*`, `settings.enabled_modules`, эндпоинт списка модулей. Пример — модуль `modules/hello` (одна сущность и один мутатор), только для тестов.
- **Приёмка:** выключенный модуль недоступен (маршруты, мутаторы, bootstrap), включение работает без перезапуска или с документированным перезапуском.

### CR-9 E2E-обвязка
- **Состав:** Playwright в `e2e/`, стек из compose, сценарии и замеры по `docs/roadmap.md` §7. Сценарии UI добавляет web. Здесь — каркас, API-сценарии (права, офлайн-очередь через протокол) и скрипт замеров с выводом чисел.
- **Зависимость:** WB-2 — для замеров на клиенте. До готовности WB-2 делаем только серверную часть.

### CR-10 API-токены и REST
- **Состав:** по `docs/roadmap.md` §5.1. Токен `plnr_<32 байта base62>`, в БД хранятся sha256 и префикс для показа. Права: `read` — только GET, MCP-инструменты на чтение; `write` — всё. В истории изменений видно, что запись сделана через токен.
- **REST `/api/v1`:** spaces, projects, tasks (фильтры: проект, статус, исполнитель, обновлено после), comments. Запись — через те же мутаторы. OpenAPI — `/api/v1/openapi.json`.
- **Приёмка:** токен показывается один раз; отозванный и просроченный токены дают 401; `read` не может писать; права пространств соблюдаются.

### CR-11 MCP
- **Состав:** `/mcp`, Streamable HTTP, `@modelcontextprotocol/sdk`, Bearer API-токен. Инструменты из `docs/roadmap.md` §5.1 со схемами zod, инструменты возвращают компактный JSON. Ошибки прав отдаются как ошибки инструмента, а не 500.
- **Приёмка:** интеграционный тест клиентом SDK — `initialize`, `tools/list`, создание и чтение задачи, отказ при `read`-токене на запись; инструкция подключения в `docs/guides/mcp.md`.
