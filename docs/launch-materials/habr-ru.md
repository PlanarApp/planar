# Трекер с local-first синхронизацией: как устроено

Planar — трекер задач для команд с локальной репликой данных в браузере: интерфейс отвечает без ожидания сети и работает офлайн. Один экземпляр — одно рабочее пространство, ставится у себя через Docker Compose. Код открыт (Apache 2.0): https://gitlab.com/planarhq/planar (зеркало: https://github.com/PlanarApp/planar). Версия 0.9.0, публичная бета.

Ниже — как устроена синхронизация. Источник: `docs/roadmap.md`, §3 и §7.

## Идея

Клиент читает и пишет в локальную базу (IndexedDB через Dexie), а не ходит за каждым экраном на сервер. Сеть нужна только для синхронизации в фоне. Отсюда мгновенный отклик и офлайн «почти бесплатно».

## Мутации — одна функция на два места

Любое изменение — именованная функция из `packages/shared/mutators`. Одна и та же функция выполняется дважды:

1. на клиенте, оптимистично, над Dexie;
2. на сервере, в транзакции Drizzle.

Обе реализации работают через общий интерфейс `Tx {get, put, del, scan}`. Сервер дополнительно проверяет права.

## Журнал изменений и «пинок»

Каждая запись на сервере добавляет строку в таблицу `changes(seq bigserial, space_id, entity, id, op, data)` и делает `NOTIFY` (PostgreSQL LISTEN/NOTIFY). WebSocket-шлюз рассылает подключённым клиентам `poke{seq}`. Клиент отвечает запросом `pull?cursor=` и получает только изменения из своих пространств. Очереди, pub/sub и кэш — в одном PostgreSQL 18, Redis не нужен.

## Офлайн и rebase

Неподтверждённые мутации лежат в очереди в IndexedDB. После каждого pull клиент берёт состояние сервера и заново применяет поверх него неподтверждённые мутации — rebase, как в Replicache. Так правки, сделанные без сети, не теряются и доходят до сервера после переподключения.

## Конфликты

Правило — last-write-wins на уровне поля. Источник истины — сервер. Это простое правило, не CRDT: одновременная правка одного и того же поля двумя людьми оставит последнюю принятую сервером.

## Бюджеты скорости

В роадмапе заданы целевые бюджеты, которые проверяются в приёмке. Это цели проекта, а не результаты замеров, которые мы здесь публикуем:

- начальный JS ≤ 200 КБ в gzip;
- холодный старт на 10 000 задач до интерактива ≤ 2 с, тёплый из IndexedDB ≤ 450 мс;
- локальная мутация до перерисовки ≤ 50 мс;
- правка в одном клиенте появляется в другом ≤ 500 мс (локальный стек).

## Стек

Node 24, NestJS 11 + Fastify, Drizzle, pg-boss, Vue 3.5 + Vite, Dexie, Tailwind 4, TipTap, Vitest и Playwright (`docs/roadmap.md`, §2).

## Вокруг синхронизации

- REST API `/api/v1` и встроенный MCP-сервер `/mcp` (Streamable HTTP) с личными токенами `plnr_…` (права `read` и `write`): `docs/guides/mcp.md`.
- Модули в `modules/*` (в репозитории 18 каталогов, например `sprints`, `time`, `forms`, `automations`, `webhooks`, `dashboards`, `docs`, `gitlab`), плагины — страницы в песочнице.
- Бэкапы и восстановление: `ops/backup.sh`, `ops/restore.sh`, `ops/upgrade.sh`.

## Попробовать

```bash
git clone https://gitlab.com/planarhq/planar.git
cd planar
cp .env.example .env   # задайте POSTGRES_PASSWORD, PLANAR_DOMAIN и остальное
docker compose up -d
```

Для настоящего сервера смотрите `docs/guides/deploy.md`. Первый визит показывает форму создания владельца — откройте сайт сразу после старта.
