# p3 module contracts

Owner — the p3 coordinator. The format of entities and mutators is as in `docs/contracts/core.md` (C-schema "General rules", "Types", "Visibility and permissions") and `core-mutators.md`. Modules follow C-modules (`modules/<id>`, package `@planar/module-<id>`, tables `<id>_<snake>`, routes `/api/<id>/`).

Contract test — `apps/api/test/modules/p3.contract.test.ts`: checks the `#### <entity>` sections and mutator tables of this file against `shared.entities` and `shared.mutators` of the modules. A module not yet in `installed.ts` is skipped; `P3_CONTRACT_STRICT=1` — a missing module is an error (checked in the module's task card).

Changes to C-* (core) are not made in this file: they are approved by the main session (C-schema v9 — `ydocs`; C-http v11 — WS `/collab`, env `PLANAR_SECRET_KEY`, entry `/f/*`; C-modules v9 — `CoreServices.execute`, `ensureSystemUser`, `storeFile`) and are put into `core.md` by the p3 task. Below they are marked "→ C-…".

## P3-collab v1 (PT-1)

### Protocol
- Hocuspocus (`@hocuspocus/server`) in the api process, WebSocket on the path `/collab` of the same HTTP server as `/ws` (→ C-http: path `/collab`; Vite dev and Caddy proxy it like `/ws`).
- Document name: `docs:<pageId>` (page of `docsPages`) or `task:<taskId>` (task description). Any other name is rejected.
- Yjs field: `Y.XmlFragment` named `default` (the default of `@tiptap/extension-collaboration`).
- Shortcut: a single api process; for several processes — `@hocuspocus/extension-redis`.

### Authorization
- Upgrade `/collab`: cookie `planar_sid` — a valid session, an active user; `Origin` = origin of `PUBLIC_URL` (as `/ws`, C-http "Session and Origin"). Otherwise the upgrade is rejected (401/403) before Hocuspocus. Bearer is not accepted.
- `onAuthenticate` for each document:
  - `docs:<id>` — the docs module is enabled, the page exists, the user is a member of its space. Role ≥ member — write; guest or an archived page — `connection.readOnly = true`.
  - `task:<id>` — the task exists, the user is a member of its space. Role ≥ member — write, guest — read only.
  - Otherwise — rejected (`forbidden` or `not_found`), the document is not loaded.
- A user removed from the space (`spaceMembers` del) or deactivated — their connections to documents of that space are closed.
- Awareness: `user: {id, name, color}`. `color` is deterministic by `userId`: index `hash(userId) mod N` in the shared cursor palette (one source for all clients). Shortcut: the server does not validate awareness.

## P3-ydoc v1 (PT-1)

### Storage
A non-synced core table (→ C-schema, "Non-synced tables"):

| table | columns |
|---|---|
| `ydocs` | `doc_id text pk` (document name, `docs:<uuid>` \| `task:<uuid>`), `state bytea not null` (`Y.encodeStateAsUpdate`), `updated_at timestamptz` |

Schema — `apps/api/src/db/schema.ts`, drizzle-kit migration.

### Loading (`onLoadDocument`)
- A `ydocs` row exists — apply `state`.
- Otherwise — build the Y.Doc from the current JSON: `docsPages.body` or `tasks.description` (`null` → empty `doc`), through the editor's ProseMirror schema. This is the migration of existing bodies: there is no separate run.
- The ProseMirror schema is **one** list of TipTap extensions for web and api, without DOM and Vue (node views are attached by web only). The server has no copy of the schema of its own.

### Saving and projection (`onStoreDocument`)
- Debounce 2 s after the last edit, at least once per 10 s during continuous editing; on closing the last connection — immediately.
- Order: write `ydocs.state` → build JSON from `default` (`yXmlFragmentToProsemirrorJSON` or `TiptapTransformer.fromYdoc`) → if the JSON differs from the current field (deep comparison) — a mutator on behalf of the **last editing** user, with normal permissions (not `system`):
  - `docs:<id>` → `docs.page.update {id, body}` (the mutator computes `text`, `files`, `updatedBy` itself);
  - `task:<id>` → `task.update {id, description}`.
- This way sync, search, REST v1, MCP and activity work as before. C-sync and C-mutators do not change.
- The mutator rejected (permissions, `conflict` on an archived page, `invalid_args` for > 512 KB) — `log.warn`, `ydocs` is already saved, the next save tries again.

### External write
- An external write is a change of `docsPages.body` or `tasks.description` not made by the projection: REST v1, MCP, a mutator from an offline client of an old version, `task.create` with a description.
- A rule without marks: if the new JSON is deeply equal to the projection of the current Y.Doc — nothing happens (so the projection does not loop). Otherwise:
  - the document is loaded in Hocuspocus — the content of `default` is replaced with the new JSON in one Y-transaction, clients receive the replacement (last write wins);
  - not loaded — the content of `default` in the stored `ydocs.state` is replaced the same way and the row is written back (PLNRAPP-185: deleting the row made a client's IndexedDB copy merge with a rebuilt Y.Doc — doubled text). Unreadable JSON — the row is deleted, the next open refuses.
- Task deletion (`task.delete`) — delete `ydocs` `task:<id>`, close the document's connections.

### Client (web)
- `Editor.vue` (`apps/web/src/task/editor/`) — an optional prop `collab?: { name: string }`. If set → Collaboration and cursor extensions (`@tiptap/extension-collaboration`, `collaboration-cursor`/`collaboration-caret` depending on the TipTap version), `HocuspocusProvider` on `/collab` of the same origin (`ws:`/`wss:`), `y-indexeddb` keyed by `v2:<name>` (PLNRAPP-185; the old store `<name>` is deleted on open); the built-in TipTap history is off (undo — Yjs). If not set — as before.
- A docs document and a task description are opened with `collab`; the comment editor — without.
- Offline: edits accumulate in IndexedDB and catch up through Yjs after reconnecting. The editor no longer writes the page body and task description through a mutator (`title`, `icon` — still `docs.page.update`).
- `readOnly` of the connection → `editable = false`.
- **DC-web v2 (instead of the soft lock CL-3):** web does not call `docs.lock`/`docs.unlock`, does not show "X is editing" and the read mode. The `docsLocks` entity and the mutators `docs.lock`/`docs.unlock` stay (DC-schema, DC-mutators v1 unchanged), their tests are green. Removal — a separate task on request.

## P3-timeline v1 (PT-2)
The `timeline` module, no synced entities or mutators.
- Web: `views` — `{id: 'timeline', label: {ru: 'Таймлайн', en: 'Timeline'}}`, project screen `/p/:projectId/timeline:timeline` (module tab key — `<moduleId>:<viewId>`, C-views). Tasks — `useProjectTasks` (C-tasks), links — `taskLinks` (F-links).
- Task bar: dates are inclusive. With both `startDate` and `dueDate` — `[startDate, dueDate]`; only one of the dates — 1 day on it; `startDate > dueDate` — drawn as `[dueDate, startDate]`. With neither — the "No dates" column, from where a drag onto the scale sets both dates (duration 1 day).
- Moving a bar — `task.update {id, startDate, dueDate}` shifting both dates; stretching an edge changes one date. A task with one date gets both when stretched.
- Scale: day, week, month; week start — `useWeekStart()`.
- Dependencies: an arrow from the end of A to the start of B for each `taskLinks {taskId: A, targetId: B, kind: 'blocks'}` row, both tasks on the scale. A violation — start of B ≤ end of A. After a move that creates a violation — a warning (toast), the arrow is highlighted; dates are not shifted.
- Virtualization: only visible rows (± margin) and the visible date range are drawn. Acceptance: 10,000 tasks, 2 s of scrolling — no long task > 50 ms (`PerformanceObserver` `longtask`).

- No row — capacity 40 h/week.

- "Task count" mode: a task counts once per assignee in the week of `dueDate`.
- Overload: week hours > capacity ("estimates" mode) — the cell is highlighted with the C-ui error token. A click on a cell — the cell's task list (`openTask`).

### Public endpoint (no login)
| method and path | input → output |
|---|---|
| `GET /api/forms/public/:slug` | → `{title, description, fields: [{key, label, required, type, options?}]}`; `type` — `text`, `longtext` (description), `email` or an F-fields field type; `options` — `select` choices |
| `POST /api/forms/public/:slug` | `{values: {<key>: value}, website: string}` → `201 {ok: true}` |

- No form, `enabled = false`, archived project, module disabled — `404` (`not_found` / `module_disabled`); the body does not reveal which condition.
- Validation by the form schema (zod, built from `fields`): required fields, limits — `title` 1–500, `description` ≤ 10,000, `email` — e-mail ≤ 254, `field:` — per F-fields; extra keys → `400 invalid_request`. JSON body ≤ 64 KB, otherwise `413`.
- Honeypot: `website` not empty → `201 {ok: true}`, no task is created.
- Rate limit by IP (the same IP source as the login limit): ≤ 5 submissions per minute and ≤ 30 per hour per IP across all forms → `429 rate_limited`. Table `forms_rate_limits(key text pk, count int, window_started_at timestamptz)` — keys `<ip>|m` and `<ip>|h`. All POST requests count, except those rejected with 404.
- Task: `task.create` through `CoreServices.execute` (C-modules v9) on behalf of the system user "Форма" (`CoreServices.ensureSystemUser('form', 'Форма')`: deactivated, no password, like "Automation"), in one transaction with `task.setField` and `attachment.create`, the form's `statusId`, `rank` — at the end, `description` — the text as paragraphs + a last paragraph "Отправитель: <email>" if an email is given.
- Attachments: a form with `allowFiles: true` in the schema (a `FormField` with `key: 'files'`) accepts `multipart/form-data`: field `payload` — JSON `{values, website}` as above, `file` fields — up to 3 files, total ≤ `MAX_UPLOAD_MB` (→ `413`). Files — `CoreServices.storeFile` (C-modules v9) as the same form system user, then `attachment.create` on the task. Multipart without `files` in the schema → `400`.
- Page `/f/<slug>`: a separate Vite entry (its own HTML, does not load the app), → C-http: path `/f/*` in dev and Caddy. Size — ≤ 30 KB gzip. No login; 404/429/400 errors — in plain text.
- App web: `settings` `forms:forms` — the project's form list, field builder, link, enable switch, personal link (v1.1).

### Personal link "reply to an existing task" (v1.1, PLNRAPP-173)
Server table `forms_links` (not synced, no entity): `id uuid pk`, `form_id`, `task_id`, `token_hash text unique` (sha256 hex of the token), `expires_at`, `single_use bool`, `used_at?`, `created_by`, `created_at`.

| method and path | input → output |
|---|---|
| `POST /api/forms/links` (login; owner/admin of the form's space or of the instance, else `403`) | `{formId, task: <uuid or KEY-N>, ttlHours?: 1–720 (168), singleUse?: bool (true)}` → `201 {token, path: '/f/<slug>?t=<token>', expiresAt}`; the task must be in the form's project (else `404`) |
| `GET /api/forms/public/:slug?t=<token>` | the usual schema + `reply: true` |
| `POST /api/forms/public/:slug?t=<token>` | the usual body → `201 {ok: true}`; instead of `task.create` — `comment.create` in the link's task (lines `<label>: <value>` in form order) + `attachment.create`, as the system user "Форма", `system: true` |

- The token is 32 random bytes (base64url), shown once; the DB keeps only the sha256, lookup by it (indexed). A wrong token, a token of another form, expired, used (single use) or a deleted task — the same `404 not_found`.
- A single-use link is claimed atomically (`update … where used_at is null`) after validation, so an invalid answer does not burn it, and released if the write fails. The honeypot does not claim.
- The same rate limit as the form POST. `comment.added` fires as for any comment; the author is deactivated and the write is `system`, so it is not `byHuman`.
- Links of a deleted form or task stay as inert rows (they never match).

## P3-gitlab v2 (PT-6)
The `gitlab` module. The server polls the GitLab REST API v4 itself; no webhooks and no `glab`.
v2: there is no workspace-wide configuration — the connection to GitLab is set in the planar project's settings, and a project has any number of connections.

### Server table (not synced)
- `gitlab_connections` — a connection of a planar project to one GitLab repository: `id uuid pk`, `project_id uuid` (planar project, no FK; deleted by a module hook together with the project), `base_url text`, `token_enc text`, `gitlab_project_id int`, `path text` (`group/name`, for display), `cursor timestamptz?` (the largest `updated_at` of processed MRs), `last_polled_at timestamptz?`, `last_error text?`, `last_error_at timestamptz?`, `created_at`; unique (`project_id`, `gitlab_project_id`).
- Migration from v1: the `gitlab_config` connection and its `gitlab_projects` repository go to every planar project that already has `gitlabMrs` rows from that repository; `gitlab_config` and `gitlab_projects` are dropped.

### Token
- AES-256-GCM, key — env `PLANAR_SECRET_KEY` (32 bytes in base64; → C-http, api environment). `token_enc = 'v1:' + base64(iv 12 bytes) + ':' + base64(tag 16 bytes) + ':' + base64(ciphertext)`; the iv is random on every write.
- Key unset or of the wrong length — saving a token gives `503 unavailable`, polling of the connection does not run (error in `last_error`).
- The token is not returned in any response and not written to the log.

### REST (only `users.role` ∈ {owner, admin}, otherwise 403; Bearer → 403 — as webhooks)
Connection `C` = `{id, projectId, baseUrl, gitlabProjectId, path, lastPolledAt, lastError, lastErrorAt}`.

| method and path | input → output |
|---|---|
| `GET /api/gitlab/projects/:projectId/connections` | → `{connections: C[]}` |
| `POST /api/gitlab/projects/:projectId/connections` | `{baseUrl, token, project}` (`baseUrl` — `http:`/`https:` without userinfo; `project` — numeric id or path `group/name`, looked up with `GET /projects/:id` and this token) → `201 {connection: C}`; unknown planar project — 404; the same repository again — the same connection with the new token and path; the same `gitlabProjectId` from another `baseUrl` — 409 |
| `PATCH /api/gitlab/connections/:id` | `{token}` → `{connection: C}`; clears `last_error` |
| `DELETE /api/gitlab/connections/:id` | → `204`; its `gitlabMrs` rows (tasks of its project) are deleted |
| `POST /api/gitlab/poll` | → `202` — an out-of-schedule poll of all connections |

### REST of the task's GitLab tab (PLNRAPP-153)
Any user with access to the task's project (`project_role`), Bearer included; no access or no task — 404, the module off — 404 `module_disabled`.

| method and path | input → output |
|---|---|
| `GET /api/gitlab/tasks/:taskId/repos` | → `{repos: {id, path}[]}` — connections of the task's project |
| `POST /api/gitlab/tasks/:taskId/poll` | → `200 {}` after a poll of the connections of the task's project (as the scheduled one) |
| `POST /api/gitlab/tasks/:taskId/branch` | `{connectionId?}` (none — the first connection) → `201 {webUrl}`; branch named by the task key from the repository's `default_branch`, an existing branch (GitLab 400) is reused; guest or read-only token — 403; no connection — 404 |
| `POST /api/gitlab/tasks/:taskId/mr` | as `branch`, then an MR from the branch into `default_branch` with title `<key>: <task title>` → `201 {webUrl}` of the MR, synced to `gitlabMrs` at once; an MR from this branch exists (GitLab 409) — 409; GitLab 401/403 — 502 |

### Polling
- pg-boss: `gitlab.tick` (cron `* * * * *`) enqueues `gitlab.poll` (singletonKey `gitlab.poll`) if there are connections and ≥ 120 s have passed since the last poll.
- Per connection: `GET {base}/api/v4/projects/:id/merge_requests?updated_after=<cursor>&order_by=updated_at&sort=asc&per_page=100&page=N`, header `PRIVATE-TOKEN`; pages by `X-Next-Page` until empty. No cursor — `updated_after` = now − 30 days. The request's `updated_after` is fixed before the page walk; the advanced cursor is stored separately.
- The cursor advances after each processed page. `updated_after` is inclusive: an MR with `updated_at = cursor` is processed again (the upsert is idempotent).
- Task key: `\b([A-Z][A-Z0-9]{1,9})-(\d+)\b` in `title`, `source_branch` (case-insensitive) and `description`; a task with such `key` and `number` is looked up only in the connection's planar project. No task — the key is skipped.
- Errors (all — in the connection's `last_error`, other connections proceed): 401/403 — `unauthorized`, polling of the connection stops until `PATCH` of the token; 404 — `not_found`; 429 — wait `Retry-After` (≤ 300 s) once, otherwise `rate_limited` and the next tick; 5xx/network — the error text, next tick; no key — `secret_key_missing`. Polling does not crash; every error is a `log.warn` without the token.
