# Contracts of the p4 module

Owner — the p4 coordinator. The format of entities and mutators is as in `docs/contracts/core.md` (C-schema "General rules", "Types", "Visibility and permissions") and `core-mutators.md`. Modules follow C-modules (`modules/<id>`, package `@planar/module-<id>`, tables `<id>_<snake>`, routes `/api/<id>/`, hooks and jobs — `docs/contracts/work.md` §C-modules v3–v4).

Contract test — `apps/api/test/modules/p4.contract.test.ts`: checks the `#### <entity>` sections and mutator tables of this file against `shared.entities` and `shared.mutators` of the modules. A module not yet in `installed.ts` is skipped; with `P4_CONTRACT_STRICT=1` a missing module is an error (checked in the module task's card).

C-* are not edited in this file; the ones approved by main (2026-10-25) are marked "→ C-…" and made by a p4 task (`versions.ts`, headings of the `core.md` parts, contract tests):
- **C-modules v11** — (1) `BackendModuleManifest.unavailable?: (q: Q) => Promise<string | null>`: null — the module can be enabled, a string — the reason code; `GET /api/modules` += `unavailable: string | null` for each module; in `ModulesSettings` the toggle of a disabled unavailable module is inactive, the reason is the text `modules.unavailable.<code>` (no key — the code). (2) `ModuleGuard` lets `/api/<id>/setup/*` of a disabled module through only for `users.role` ∈ {owner, admin} (otherwise `403 forbidden`, Bearer → 403; the check is in the guard, the module checks permissions again); `FrontendModuleManifest.setup?: Lazy<{}>` — `ModulesSettings` shows "Configure" (the component in a dialog) also for a disabled module and loads the module's web part lazily. Test: member → 403 on `setup` of a disabled module. (3) `CommandDef.newTaskMenu?: boolean` — the command (with `when`) is also visible in the view's "New task" button menu; `run` gets the same `CommandCtx`.
- **C-mutators v5** — `settings.set {id: 'enabled_modules'}`: an id that was not among the enabled ones and whose module has `unavailable` ≠ null → `invalid_args` (the message is the reason code). Checked on the server only (on the client — no check, rollback by the response).

Common to all p4 modules:
- A module mutator that creates core rows calls the `run` of the core mutator from `domainMutators` (`@planar/shared`) with the same `tx` and `ctx` — the same rules and permissions; a direct `tx.put` into core tables only where stated.
- Task deletion hook: `afterMutation`, a `tasks` write with `op: 'del'` → the module's rows of this task are deleted through `api.sys`.
- A system call of a mutator (`MutatorCtx` has no `system` flag, C-mutators stays unchanged): "system only" = `users[ctx.userId].deactivatedAt ≠ null` (the core's system users are deactivated; deactivated people sign in neither by session nor by token). For `write: server` entities the entity itself is enough.
- "Today" in time zone `tz` — `Intl.DateTimeFormat('en-CA', {timeZone: tz})` applied to server time; an invalid IANA name (`Intl` throws) → `invalid_args`.

## P4-recurring v2 (PF-1)

v2: "system only" — by the rule above; `recurring.spawn` += `taskId` (the template at enqueue time); the default time zone in web is the browser's.
Module `recurring`.

#### recurringRules
scope: space · write: member · bootstrap: yes · indexes: spaceId, taskId

| field | type | note |
|---|---|---|
| `id` | uuid | |
| `spaceId` | uuid | from the task |
| `taskId` | uuid | the current instance is the template of the next one; unique; no FK (the task deletion hook deletes the rule) |
| `kind` | enum(interval,weekdays,after_done) | |
| `every` | int | `interval`, `after_done` — a step of 1–365 `unit`s; `weekdays` — every N weeks, 1–52 |
| `unit` | enum(day,week,month) | for `weekdays` — always `week` |
| `weekdays` | json | `number[]` 0–6 (0 — Sunday), ascending, no repeats; non-empty for `weekdays`, `[]` for the others; not null |
| `anchorDate` | date | start of the schedule |
| `nextDate` | date? | `dueDate` of the next instance; for `after_done` — null |
| `timezone` | text | IANA; "today" and the completion date are computed in it |
| `createdBy` | uuid | |
| `createdAt` | ts | |
| `updatedAt` | ts | |

The time zone is stored in the rule (the core has none for a project); web fills in the browser's zone by default (`Intl.DateTimeFormat().resolvedOptions().timeZone`).

| mutator | args | rules |
|---|---|---|
| `recurring.set` | `id, taskId, kind, every, unit, weekdays, timezone, anchorDate?` | no task → `not_found`; fields not matching the table above → `invalid_args`; if the task already has a rule with a different `id`, that rule is updated; `anchorDate` defaults to the task's `dueDate`, otherwise today in `timezone`; `nextDate = nextOccurrence(rule, task.dueDate ?? anchorDate)`, for `after_done` — null; `createdBy = ctx.userId` on creation |
| `recurring.remove` | `taskId` | deletes the task's rule; none — nothing |
| `recurring.advance` | `id, taskId, nextDate: date\|null` | system only (see the rule above), otherwise `forbidden`; the rule moves to the new instance |

Pure functions (`modules/recurring/shared`, exported; dates are `YYYY-MM-DD`, no time zones):
- `nextOccurrence(rule, after): date` — the smallest schedule date strictly greater than `after`:
  - `interval` + `day`/`week` — `anchorDate + k·every·(1|7)` days, k ≥ 0;
  - `interval` + `month` — the month of `anchorDate` + k·every, the day is `min(day of anchorDate, days in the month)` (Jan 31 → Feb 28/29 → Mar 31);
  - `weekdays` — dates ≥ `anchorDate` whose weekday is in `weekdays` and whose ISO week number (weeks start on Monday), counted from the week of `anchorDate`, is divisible by `every`.
- `duePeriod(rule, today, span): date | null` — for schedules: the largest schedule date `o ≥ nextDate` with `o − span ≤ today`; none — null. `span` — days from `startDate` to `dueDate` of the current instance (0 if either date is missing). Missed periods are not caught up: one instance is created — the latest that has come.
- `afterDoneDue(rule, completedDate): date` — `completedDate + every·unit` (month — as above, from the day of `completedDate`).

Instance creation:
- Cron `recurring.tick` (`*/10 * * * *`): rules with `kind ≠ after_done` and `duePeriod(rule, today in timezone, span) ≠ null` → `recurring.spawn {ruleId, period, taskId}` (`period` = this date, `taskId` — the template at enqueue time, `singletonKey` = `ruleId:period`).
- `after_done`: `afterMutation` hook — a `tasks` put with `before.completedAt = null`, `after.completedAt ≠ null`, `after` status of category `done` (not `cancelled`), and the task has an `after_done` rule → `api.enqueue('recurring.spawn', {ruleId, period: taskId, taskId})`. The new instance's `dueDate` is `afterDoneDue(rule, date of completedAt in timezone)`.
- `recurring.spawn` — `JobApi.execute(systemUserId, muts, {system: true, prepare})`. `prepare`: locks the rule row (`select … for update`), the rule exists and its `taskId` = the job's `taskId`, then `insert into recurring_runs … on conflict do nothing`; not inserted or the check failed → `false`. Job retry, two workers, two ticks — one instance per (rule, period).
- `muts`: `task.create` — `projectId`, `parentId`, `title`, `description`, `priority` of the template; `statusId` — the first by `rank` status of the space in category `todo`, otherwise `backlog`, otherwise the template's status; `rank` — after the largest in the project; `dueDate` — the period (or `afterDoneDue`), `startDate = dueDate − span` (if the template has both dates, otherwise only `dueDate`, and for a template without `dueDate` also only `dueDate`); `assignees` — the template's assignees who are still space members; `labels` — the template's labels. Then `task.update {fields}` (if not `{}`), `checklist.add` for each item (same `text` and `rank`, `done: false`), `recurring.advance {id, taskId: new, nextDate: nextOccurrence(rule, period)}` (for `after_done` — null). Subtasks, comments, attachments are not copied.
- Server table `recurring_runs`: `rule_id uuid`, `period text` (a date or the id of the template task), `task_id uuid`, `created_at`; PK (rule_id, period).
- Web: `taskPanels` `recurring:repeat` "Repeat" — mode, N, unit, weekdays, time zone, next date (`nextDate`), "Remove repeat".
- Acceptance: unit tests of the functions (the 31st, a leap year, `weekdays` every other week, the day boundary UTC/`Europe/Moscow`); integration with `push: {boss: true}`: two `recurring.tick` in a row and a parallel `spawn` — one instance; `after_done` — one instance; copy of assignees, labels, checklist and `fields`; the author is the system user.

Format of `data` (zod `taskTemplateSchema`, `projectTemplateSchema` — exported from `modules/templates/shared`):
```ts
type TemplateTask = {
  title: string;                 // 1–500
  description: Doc | null;       // C-schema doc
  priority: 0 | 1 | 2 | 3 | 4;
  dueInDays: number | null;      // int 0–3650: dueDate = today + N
  startInDays: number | null;    // int 0–3650
  fields: { name: string; type: FieldType; value: unknown }[]; // ≤ 50; applied to the project field with the same name and type, otherwise skipped; value per F-fields, otherwise skipped
  labels: string[];              // space label names, ≤ 50; no such label → skipped
  assigneeIds: string[];         // ≤ 20; not a space member → skipped
  checklist: string[];           // ≤ 100, each 1–500
};
type TaskTemplate = TemplateTask & { subtasks: TemplateTask[] };          // ≤ 50, one level
type ProjectTemplate = {
  project: { description: Doc | null; color: string | null; icon: string | null };
  statuses: { name: string; category: StatusCategory; color: string }[]; // ≤ 30
  labels: { name: string; color: string }[];                              // ≤ 100
  fields: { name: string; type: FieldType; options: object }[];           // ≤ 50
  tasks: (TaskTemplate & { status: string })[];                           // ≤ 500; status is a name from statuses
};
```
Status and label names are compared case-insensitively after trim.

| mutator | args | rules |
|---|---|---|
| `templates.create` | `id, spaceId, kind, name, data, description?` | `data` not matching the schema of `kind` → `invalid_args`; `createdBy = ctx.userId` |
| `templates.update` | `id, name?, description?, data?` | `data` is checked by the schema of the row's `kind` |
| `templates.delete` | `id` | |
| `templates.createTask` | `templateId, projectId, statusId, rank, today, ids, parentId?` | a template with `kind = task` from the same space as the project, otherwise `invalid_args`; `today: date` — the client's today; `ids: uuid[]` — new ids in the order of `templateIdPlan(kind, data)`, too few → `invalid_args`; the task and subtasks are `task.create` (+ `task.setField`, `checklist.add`) through `domainMutators`; ranks of subtasks and items — `generateNKeysBetween(null, null, n)` |
| `templates.createProject` | `templateId, projectId, name, key, rank, today, ids` | a template with `kind = project`; `project.create` in the template's space; statuses and labels missing by name — `status.create` and `label.create` (to the end by `rank`); fields — `field.create`; tasks — as in `templates.createTask`, `statusId` by the name in `status`; permissions are those of the core mutators (`status.create` — admin: a non-admin who needs a new status → `forbidden`) |

- `templateIdPlan(kind, data): {count: number}` and the order in which `ids` are consumed — one function in `modules/templates/shared`, shared by client and server. Mutators are deterministic (no `Date`, `Math.random`).
- Save as template: `taskToTemplate(taskId, read)` and `projectToTemplate(projectId, read)` — `modules/templates/shared`, data from the replica; then `templates.create`. `dueInDays`/`startInDays` — the difference between the task's dates and today (negative → null); subtasks are direct children.
- Web: `commands` `templates:newTask` "Task from template…" (`when: projectId`, → C-modules v11 `newTaskMenu: true`), `templates:saveTask` "Save as template" (one selected or open task); `settings` `templates:templates` — the list of the space's templates, rename, delete, "Create project from template", "Save project as template".
- Acceptance: the `data` schema (limits, invalid ones — `invalid_args`); `createTask` on the server and in memory-tx gives the same rows; too few `ids`; a project from a template creates the missing statuses and labels and does not duplicate existing ones; a round trip "save → create" preserves fields, checklist, subtasks.

## P4-email v2 (PF-4)

v2: the SMTP error of the test email is `502 unavailable` (C-http has no `smtp_error` code); the `application/x-www-form-urlencoded` parser is only on the unsubscribe route; tasks of archived projects are excluded from the digest.
Module `email`. SMTP — `nodemailer` (a dependency of `apps/api` or of the module package; Q1 — approved). Depends on → C-modules v11: unavailability without settings and the routes `/api/email/setup/*` of a disabled module.

### Server tables (not synced)
- `email_config` (one row, `id text pk = 'default'`): `host text`, `port int` (1–65535), `secure bool` (true — TLS at once, false — STARTTLS if the server offers it), `username text?`, `password_enc text?` (format and key — P3-gitlab "Token", `PLANAR_SECRET_KEY`), `from_address text` (`addr` or `Name <addr>`), `updated_at`.
- `email_outbox`: `notification_id uuid pk`, `user_id uuid` (FK `users` cascade), `status text check (sending,sent,failed,skipped)`, `error text?`, `created_at`, `sent_at timestamptz?`.
- `email_digests`: `user_id uuid` (FK cascade), `date date`, `status text check (sending,sent,failed,skipped)`, `error text?`, `created_at`; PK (user_id, date).

### Availability
- `unavailable` (→ C-modules v11): no `email_config` row, or an empty `host` or `from_address` → `'smtp_not_configured'`; otherwise null.

### REST
`/api/email/setup/*` — only `users.role` ∈ {owner, admin}, otherwise 403; Bearer → 403.

| method and path | input → output |
|---|---|
| `GET /api/email/setup/config` | → `{host, port, secure, username, hasPassword, from, configured}` (`configured` = `unavailable` returned null) |
| `PUT /api/email/setup/config` | `{host?, port?, secure?, username?: string\|null, password?: string\|null, from?}` → as GET; `password: null` — delete; no key — password `503 unavailable`; `from` — an RFC 5322 address (a single entry) |
| `POST /api/email/setup/test` | `{to: email}` → `200 {ok: true}`; SMTP error → `502 unavailable` (the SMTP error text in `message`, without the password) |
| `GET /api/email/unsubscribe?t=<token>` | no sign-in → HTML: what is being unsubscribed, a button (a POST form to the same address); invalid token → `400` HTML |
| `POST /api/email/unsubscribe?t=<token>` | no sign-in; form body or RFC 8058 `List-Unsubscribe=One-Click` (`application/x-www-form-urlencoded` is parsed only on this route, the global Fastify parser is not registered) → `email.setPrefs` as the system for the token owner (`notify` or `digest` = false) → `200` HTML "You are unsubscribed"; invalid token → `400` |

Unsubscribe token: `<userId>.<kind>.<sig>`, `kind` ∈ {notify, digest}, `sig` = base64url(HMAC-SHA256(key `PLANAR_SECRET_KEY`, `email-unsub:v1:<userId>:<kind>`)); compared with `timingSafeEqual`; no expiry. No key — no emails, unsubscribe returns `503`.

### Sending
- An email goes only to an active user with `users.email`. Subject, text and simple HTML (inline styles, all substitutions escaped); language — ru. Links — `PUBLIC_URL` + path (`/t/<KEY>-<number>` for a task, otherwise `notifications.url` by the Web Push rules). Headers `List-Unsubscribe: <…/api/email/unsubscribe?t=…>`, `List-Unsubscribe-Post: List-Unsubscribe=One-Click`.
- Cron `email.notify` (`* * * * *`): `notifications` with `kind` ∈ {assigned, mentioned, chat_mention}, `readAt = null`, `createdAt` in [now − 24 h, now − 10 min], without an `email_outbox` row, `emailPrefs.notify ≠ false` — up to 200 per tick. For each: `insert email_outbox (sending) on conflict do nothing` (not inserted — skip), re-check `readAt` (read — `skipped`), send, `sent`/`failed` + `error`. No retries: at most one email per notification.
- Cron `email.digest` (`0 * * * *`): if the hour in `settings.timezone` (default UTC) is ≥ 8 — users with `digest = true` and no `email_digests` row for today's date: `insert … sending on conflict do nothing`; the content is unread notifications for 24 h (≤ 50) and the user's open tasks (assignee, category not done/cancelled, project not archived) with `dueDate ≤ today`; empty — `skipped` without an email.
- The password and tokens do not appear in responses or logs (`log.warn` of SMTP errors omits them).
- Web: `setup` (→ C-modules v11; the same component is `settings` `email:setup`, `adminOnly`, when the module is enabled) — host, port, TLS, login, password (an input field, never displayed), sender, "Send test email"; `settings` `email:prefs` "Email" (all users) — toggles `notify`, `digest`.
- Acceptance — against the test's own SMTP stub (`net`, keeps the emails): the 10 min delay and skipping read ones, once with two ticks, the digest once a day, unsubscribe by token (invalid signature → 400), password encryption, `unavailable` without settings.

### iframe
- `<iframe src="url" sandbox="allow-scripts allow-forms allow-same-origin" referrerpolicy="no-referrer">` (Q2): `allow-same-origin` is safe only because the plugin host ≠ the app host (`checkPluginUrl` at registration and before showing). No `allow-popups`, `allow-top-navigation`.
- The `planar_sid` cookie has no `Domain` attribute (host-only); checked by a test (the sign-in `Set-Cookie` header).
- CSP: before the first plugin iframe web adds to `<head>` `<meta http-equiv="Content-Security-Policy" content="frame-src <origins of enabled plugins separated by spaces>">` (no plugins — `frame-src 'none'`). The policy only narrows: a plugin added after the page loaded is shown after a reload (hint "Reload the page").
- The plugin gets no cookies, tokens or data beyond the protocol responses.

### postMessage protocol v1
All messages are objects with `planar: 1` and `type`. The host sends only `iframe.contentWindow.postMessage(msg, plugin.origin)`. The host accepts a message only if `event.source === iframe.contentWindow`, `event.origin === plugin.origin`, `data.planar === 1` and `type` is known; otherwise it silently ignores it (no reply, `console.warn`).

| type | direction | fields | reply |
|---|---|---|---|
| `ready` | plugin → host | — | `init` |
| `init` | host → plugin | `plugin: {id}`, `user: {id, name, login, role}`, `context: {point: 'taskPanel', taskId, projectId, spaceId} \| {point: 'page'}`, `permissions`, `locale: 'ru'\|'en'`, `theme: 'light'\|'dark'` | — |
| `query` | plugin → host | `id: string`, `entity: PluginEntity`, `where?: {<field>: value}`, `ids?: uuid[]`, `limit?: int ≤ 500` | `result` with `rows` |
| `mutate` | plugin → host | `id`, `name`, `args` | `result` |
| `navigate` | plugin → host | `path` | — |
| `resize` | plugin → host | `height: int` | — |
| `result` | host → plugin | `id`, `ok: true, rows?` or `ok: false, error: {code, message}` | — |

- `query`: `entity` ∉ `permissions.read` → `forbidden`; `where` — only `id` and the fields of the entity's `indexes` (C-schema), otherwise `invalid_request`; data comes from the local replica (what the user sees); `users` — only `{id, name, login, avatarFile}`; `limit` defaults to 100.
- `mutate`: a mutator not allowed by `permissions.write` → `forbidden` without a request; otherwise `POST /api/plugins/:id/mutate {name, args}` (session; Bearer → 403): the server checks that the plugin exists, is `enabled` and the mutator is allowed (otherwise `403 forbidden`), and runs `executeMutations` as the session user (their permissions apply too; mutator errors follow C-http). The result arrives through sync.
- `navigate`: `path` starts with `/`, not `//` and not `/\` → `router.push`; otherwise ignored.
- `resize`: `height` is clamped to 40–2000 px (`taskPanel` only).
- A task change means a new iframe (key — `taskId`).
- Web: `taskPanels` `plugins:panel` "Plugins" — the iframe of each enabled plugin with a `taskPanel`; `nav` `plugins:pages` — links to `/m/plugins/p/:pluginId` for plugins with a `page`; `settings` `plugins:admin` (`adminOnly`) — registration, permissions, points, enabling.
- Example — `examples/plugin-hello/index.html` (a static page without a build): on `init` it shows the user and the task title (`query tasks`), a "Comment" button (`mutate comment.create`).
- Acceptance: bridge tests — foreign `origin`, foreign `source`, `planar ≠ 1` → ignored; `query` outside `read` and `mutate` outside `write` → `forbidden`; server — `403` on a mutator outside permissions, a disabled plugin, Bearer; `checkPluginUrl` — the app origin, `javascript:`, userinfo, `http:` not localhost.
