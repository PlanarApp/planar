# Контракты модуля p4

Владелец — координатор p4. Формат сущностей и мутаторов — как в `docs/contracts/core.md` (C-schema «Общие правила», «Типы», «Видимость и права») и `core-mutators.md`. Модули — по C-modules (`modules/<id>`, пакет `@planar/module-<id>`, таблицы `<id>_<snake>`, маршруты `/api/<id>/`, хуки и задачи — `docs/contracts/work.md` §C-modules v3–v4).

Контрактный тест — `apps/api/test/modules/p4.contract.test.ts`: сверяет разделы `#### <сущность>` и таблицы мутаторов этого файла с `shared.entities` и `shared.mutators` модулей. Модуль, которого ещё нет в `installed.ts`, пропускается; `P4_CONTRACT_STRICT=1` — отсутствие модуля = ошибка (проверка в карточке задачи модуля).

Правки C-* в этом файле не делаются; одобренные главной (2026-10-25) помечены «→ C-…» и вносятся задачей p4 (`versions.ts`, заголовки частей `core.md`, контрактные тесты):
- **C-modules v11** — (1) `BackendModuleManifest.unavailable?: (q: Q) => Promise<string | null>`: null — модуль можно включить, строка — код причины; `GET /api/modules` += `unavailable: string | null` у каждого модуля; `ModulesSettings` — переключатель выключенного недоступного модуля неактивен, причина — текст `modules.unavailable.<код>` (нет ключа — код). (2) `ModuleGuard` пропускает `/api/<id>/setup/*` выключенного модуля только для `users.role` ∈ {owner, admin} (иначе `403 forbidden`, Bearer → 403; проверка в guard, модуль проверяет права ещё раз); `FrontendModuleManifest.setup?: Lazy<{}>` — `ModulesSettings` показывает «Настроить» (компонент в диалоге) и у выключенного модуля, грузит web-часть модуля лениво. Тест: member → 403 на `setup` выключенного модуля. (3) `CommandDef.newTaskMenu?: boolean` — команда (с `when`) видна и в меню кнопки «Новая задача» вида; `run` получает тот же `CommandCtx`.
- **C-mutators v5** — `settings.set {id: 'enabled_modules'}`: id, которого не было во включённых и у модуля `unavailable` ≠ null, → `invalid_args` (сообщение — код причины). Проверка только на сервере (на клиенте — без проверки, откат по ответу).

Общее для всех модулей p4:
- Мутатор модуля, создающий строки ядра, вызывает `run` мутатора ядра из `domainMutators` (`@planar/shared`) с теми же `tx` и `ctx` — те же правила и права; прямой `tx.put` в таблицы ядра — только там, где это сказано.
- Хук удаления задачи: `afterMutation`, запись `tasks` с `op: 'del'` → строки модуля этой задачи удаляются через `api.sys`.
- Системный вызов мутатора (`MutatorCtx` флага `system` не имеет, C-mutators не меняем): «только система» = `users[ctx.userId].deactivatedAt ≠ null` (системные пользователи ядра деактивированы; деактивированные люди не входят ни сессией, ни токеном). Для сущностей `write: server` достаточно самой сущности.
- «Сегодня» в часовом поясе `tz` — `Intl.DateTimeFormat('en-CA', {timeZone: tz})` от серверного времени; неверный IANA (`Intl` бросает) → `invalid_args`.

## P4-recurring v2 (PF-1)

v2: «только система» — по правилу вступления; в `recurring.spawn` += `taskId` (образец на момент постановки); пояс по умолчанию в web — браузера.
Модуль `recurring`.

#### recurringRules
scope: space · write: member · bootstrap: yes · indexes: spaceId, taskId

| поле | тип | примечание |
|---|---|---|
| `id` | uuid | |
| `spaceId` | uuid | из задачи |
| `taskId` | uuid | текущий экземпляр — образец следующего; уникально; без FK (хук удаления задачи удаляет правило) |
| `kind` | enum(interval,weekdays,after_done) | |
| `every` | int | `interval`, `after_done` — шаг 1–365 единиц `unit`; `weekdays` — каждые N недель, 1–52 |
| `unit` | enum(day,week,month) | у `weekdays` — всегда `week` |
| `weekdays` | json | `number[]` 0–6 (0 — вс), по возрастанию, без повторов; у `weekdays` непустой, у остальных `[]`; не null |
| `anchorDate` | date | начало расписания |
| `nextDate` | date? | `dueDate` следующего экземпляра; у `after_done` — null |
| `timezone` | text | IANA; в нём считаются «сегодня» и дата завершения |
| `createdBy` | uuid | |
| `createdAt` | ts | |
| `updatedAt` | ts | |

Часовой пояс хранится в правиле (в ядре у проекта его нет); web по умолчанию подставляет пояс браузера (`Intl.DateTimeFormat().resolvedOptions().timeZone`).

| мутатор | args | правила |
|---|---|---|
| `recurring.set` | `id, taskId, kind, every, unit, weekdays, timezone, anchorDate?` | нет задачи → `not_found`; поля не по таблице выше → `invalid_args`; у задачи уже есть правило с другим `id` — обновляется оно; `anchorDate` по умолчанию — `dueDate` задачи, иначе сегодня в `timezone`; `nextDate = nextOccurrence(rule, task.dueDate ?? anchorDate)`, у `after_done` — null; `createdBy = ctx.userId` при создании |
| `recurring.remove` | `taskId` | удаляет правило задачи; нет — ничего |
| `recurring.advance` | `id, taskId, nextDate: date\|null` | только система (вступление), иначе `forbidden`; правило переходит на новый экземпляр |

Чистые функции (`modules/recurring/shared`, экспорт; даты — `YYYY-MM-DD`, без часовых поясов):
- `nextOccurrence(rule, after): date` — наименьшая дата расписания строго больше `after`:
  - `interval` + `day`/`week` — `anchorDate + k·every·(1|7)` дней, k ≥ 0;
  - `interval` + `month` — месяц `anchorDate` + k·every, число — `min(день anchorDate, дней в месяце)` (31 янв → 28/29 фев → 31 мар);
  - `weekdays` — даты ≥ `anchorDate` с днём недели из `weekdays`, у которых номер ISO-недели (неделя с понедельника) от недели `anchorDate` делится на `every`.
- `duePeriod(rule, today, span): date | null` — для расписаний: наибольшая дата расписания `o ≥ nextDate` с `o − span ≤ today`; нет — null. `span` — дней от `startDate` до `dueDate` текущего экземпляра (0, если одной из дат нет). Пропущенные периоды не догоняются: создаётся один экземпляр — последний наступивший.
- `afterDoneDue(rule, completedDate): date` — `completedDate + every·unit` (месяц — как выше от дня `completedDate`).

Создание экземпляра:
- Cron `recurring.tick` (`*/10 * * * *`): правила `kind ≠ after_done` с `duePeriod(rule, сегодня в timezone, span) ≠ null` → `recurring.spawn {ruleId, period, taskId}` (`period` = эта дата, `taskId` — образец при постановке, `singletonKey` = `ruleId:period`).
- `after_done`: хук `afterMutation` — запись `tasks` put, `before.completedAt = null`, `after.completedAt ≠ null`, статус `after` категории `done` (не `cancelled`), у задачи правило `after_done` → `api.enqueue('recurring.spawn', {ruleId, period: taskId, taskId})`. `dueDate` нового — `afterDoneDue(rule, дата completedAt в timezone)`.
- `recurring.spawn` — `JobApi.execute(systemUserId, muts, {system: true, prepare})`. `prepare`: блокирует строку правила (`select … for update`), правило есть и его `taskId` = `taskId` из данных задачи, затем `insert into recurring_runs … on conflict do nothing`; не вставилось или проверка не прошла → `false`. Повтор задачи, два воркера, два тика — один экземпляр на (правило, период).
- `muts`: `task.create` — `projectId`, `parentId`, `title`, `description`, `priority` образца; `statusId` — первый по `rank` статус пространства категории `todo`, иначе `backlog`, иначе статус образца; `rank` — после наибольшего в проекте; `dueDate` — период (или `afterDoneDue`), `startDate = dueDate − span` (если у образца есть обе даты, иначе только `dueDate`, а у образца без `dueDate` — тоже только `dueDate`); `assignees` — исполнители образца, ещё участники пространства; `labels` — метки образца. Затем `task.update {fields}` (если не `{}`), `checklist.add` на каждый пункт (тот же `text` и `rank`, `done: false`), `recurring.advance {id, taskId: новый, nextDate: nextOccurrence(rule, period)}` (у `after_done` — null). Подзадачи, комментарии, вложения не копируются.
- Серверная таблица `recurring_runs`: `rule_id uuid`, `period text` (дата или id задачи-образца), `task_id uuid`, `created_at`; PK (rule_id, period).
- Web: `taskPanels` `recurring:repeat` «Повтор» — режим, N, единица, дни недели, часовой пояс, следующая дата (`nextDate`), «Убрать повтор».
- Приёмка: юнит-тесты функций (31-е число, високосный год, `weekdays` через неделю, граница суток UTC/`Europe/Moscow`); интеграция с `push: {boss: true}`: два `recurring.tick` подряд и параллельный `spawn` — один экземпляр; `after_done` — один экземпляр; копия исполнителей, меток, чек-листа и `fields`; автор — системный пользователь.

Формат `data` (zod `taskTemplateSchema`, `projectTemplateSchema` — экспорт `modules/templates/shared`):
```ts
type TemplateTask = {
  title: string;                 // 1–500
  description: Doc | null;       // C-schema doc
  priority: 0 | 1 | 2 | 3 | 4;
  dueInDays: number | null;      // int 0–3650: dueDate = today + N
  startInDays: number | null;    // int 0–3650
  fields: { name: string; type: FieldType; value: unknown }[]; // ≤ 50; применяется к полю проекта с тем же name и type, иначе пропуск; value — по F-fields, иначе пропуск
  labels: string[];              // имена меток пространства, ≤ 50; нет метки — пропуск
  assigneeIds: string[];         // ≤ 20; не участник пространства — пропуск
  checklist: string[];           // ≤ 100, каждый 1–500
};
type TaskTemplate = TemplateTask & { subtasks: TemplateTask[] };          // ≤ 50, один уровень
type ProjectTemplate = {
  project: { description: Doc | null; color: string | null; icon: string | null };
  statuses: { name: string; category: StatusCategory; color: string }[]; // ≤ 30
  labels: { name: string; color: string }[];                              // ≤ 100
  fields: { name: string; type: FieldType; options: object }[];           // ≤ 50
  tasks: (TaskTemplate & { status: string })[];                           // ≤ 500; status — имя из statuses
};
```
Имена статусов и меток сравниваются без учёта регистра после trim.

| мутатор | args | правила |
|---|---|---|
| `templates.create` | `id, spaceId, kind, name, data, description?` | `data` не по схеме `kind` → `invalid_args`; `createdBy = ctx.userId` |
| `templates.update` | `id, name?, description?, data?` | `data` — по схеме `kind` строки |
| `templates.delete` | `id` | |
| `templates.createTask` | `templateId, projectId, statusId, rank, today, ids, parentId?` | шаблон `kind = task` того же пространства, что проект, иначе `invalid_args`; `today: date` — сегодня клиента; `ids: uuid[]` — новые id в порядке `templateIdPlan(kind, data)`, не хватает → `invalid_args`; задача и подзадачи — `task.create` (+ `task.setField`, `checklist.add`) через `domainMutators`; ранги подзадач и пунктов — `generateNKeysBetween(null, null, n)` |
| `templates.createProject` | `templateId, projectId, name, key, rank, today, ids` | шаблон `kind = project`; `project.create` в пространстве шаблона; статусы и метки, которых нет по имени, — `status.create` и `label.create` (в конец по `rank`); поля — `field.create`; задачи — как `templates.createTask`, `statusId` — по имени `status`; права — как у мутаторов ядра (`status.create` — admin: не admin и нужен новый статус → `forbidden`) |

- `templateIdPlan(kind, data): {count: number}` и порядок расхода `ids` — одна функция `modules/templates/shared`, общая для клиента и сервера. Мутаторы детерминированы (без `Date`, `Math.random`).
- Сохранение как шаблон: `taskToTemplate(taskId, read)` и `projectToTemplate(projectId, read)` — `modules/templates/shared`, данные из реплики; затем `templates.create`. `dueInDays`/`startInDays` — разность дат задачи и сегодня (отрицательная → null); подзадачи — прямые дети.
- Web: `commands` `templates:newTask` «Задача из шаблона…» (`when: projectId`, → C-modules v11 `newTaskMenu: true`), `templates:saveTask` «Сохранить как шаблон» (одна выбранная или открытая задача); `settings` `templates:templates` — список шаблонов пространства, переименование, удаление, «Создать проект из шаблона», «Сохранить проект как шаблон».
- Приёмка: схема `data` (лимиты, неверные — `invalid_args`); `createTask` на сервере и в memory-tx даёт те же строки; нехватка `ids`; проект из шаблона создаёт недостающие статусы и метки и не дублирует существующие; круговая проверка «сохранить → создать» сохраняет поля, чек-лист, подзадачи.

## P4-email v2 (PF-4)

v2: ошибка SMTP тестового письма — `502 unavailable` (кода `smtp_error` в C-http нет); парсер `application/x-www-form-urlencoded` — только у маршрута отписки; в дайджест не попадают задачи архивных проектов.
Модуль `email`. SMTP — `nodemailer` (зависимость `apps/api` или пакета модуля; Q1 — одобрено). Зависит от → C-modules v11: недоступность без настроек и маршруты `/api/email/setup/*` у выключенного модуля.

### Серверные таблицы (не синхронизируются)

- `email_outbox`: `notification_id uuid pk`, `user_id uuid` (FK `users` cascade), `status text check (sending,sent,failed,skipped)`, `error text?`, `created_at`, `sent_at timestamptz?`.
- `email_digests`: `user_id uuid` (FK cascade), `date date`, `status text check (sending,sent,failed,skipped)`, `error text?`, `created_at`; PK (user_id, date).

### Доступность
- `unavailable` (→ C-modules v11): нет строки `email_config`, пустые `host` или `from_address` → `'smtp_not_configured'`; иначе null.

### REST
`/api/email/setup/*` — только `users.role` ∈ {owner, admin}, иначе 403; Bearer → 403.

| метод и путь | вход → выход |
|---|---|
| `GET /api/email/setup/config` | → `{host, port, secure, username, hasPassword, from, configured}` (`configured` = `unavailable` вернул null) |
| `PUT /api/email/setup/config` | `{host?, port?, secure?, username?: string\|null, password?: string\|null, from?}` → как GET; `password: null` — удалить; ключа нет — пароль `503 unavailable`; `from` — адрес по RFC 5322 (одна запись) |
| `POST /api/email/setup/test` | `{to: email}` → `200 {ok: true}`; ошибка SMTP → `502 unavailable` (текст ошибки SMTP в `message`, без пароля) |
| `GET /api/email/unsubscribe?t=<token>` | без входа → HTML: что отписывается, кнопка (форма POST на тот же адрес); неверный токен → `400` HTML |
| `POST /api/email/unsubscribe?t=<token>` | без входа; тело формы или RFC 8058 `List-Unsubscribe=One-Click` (`application/x-www-form-urlencoded` разбирается только на этом маршруте, глобальный парсер Fastify не регистрируется) → `email.setPrefs` от системы для владельца токена (`notify` или `digest` = false) → `200` HTML «Вы отписаны»; неверный токен → `400` |

Токен отписки: `<userId>.<kind>.<sig>`, `kind` ∈ {notify, digest}, `sig` = base64url(HMAC-SHA256(ключ `PLANAR_SECRET_KEY`, `email-unsub:v1:<userId>:<kind>`)); сравнение `timingSafeEqual`; без срока. Ключа нет — писем нет, отписка `503`.

### Отправка
- Письмо — только активному пользователю с `users.email`. Тема, текст и простой HTML (инлайн-стили, все подстановки экранированы); язык — ru. Ссылки — `PUBLIC_URL` + путь (`/t/<KEY>-<number>` для задачи, иначе `notifications.url` по правилам Web Push). Заголовки `List-Unsubscribe: <…/api/email/unsubscribe?t=…>`, `List-Unsubscribe-Post: List-Unsubscribe=One-Click`.
- Cron `email.notify` (`* * * * *`): `notifications` с `kind` ∈ {assigned, mentioned, chat_mention}, `readAt = null`, `createdAt` в [сейчас − 24 ч, сейчас − 10 мин], без строки `email_outbox`, `emailPrefs.notify ≠ false` — до 200 за тик. На каждое: `insert email_outbox (sending) on conflict do nothing` (не вставилось — пропуск), повторная проверка `readAt` (прочитано — `skipped`), отправка, `sent`/`failed` + `error`. Повторов нет: не больше одного письма на уведомление.
- Cron `email.digest` (`0 * * * *`): если в `settings.timezone` (по умолчанию UTC) час ≥ 8 — пользователи с `digest = true` без строки `email_digests` на сегодняшнюю дату: `insert … sending on conflict do nothing`, содержимое — непрочитанные уведомления за 24 ч (≤ 50) и открытые задачи пользователя (исполнитель, категория не done/cancelled, проект не архивный) с `dueDate ≤ сегодня`; пусто — `skipped` без письма.
- Пароль и токены не попадают в ответы и логи (`log.warn` ошибок SMTP — без них).
- Web: `setup` (→ C-modules v11; тот же компонент — `settings` `email:setup`, `adminOnly`, у включённого модуля) — хост, порт, TLS, логин, пароль (поле ввода, не показывается), отправитель, «Отправить тестовое письмо»; `settings` `email:prefs` «Email» (все пользователи) — переключатели `notify`, `digest`.
- Приёмка — против своей заглушки SMTP в тесте (`net`, сохраняет письма): задержка 10 мин и пропуск прочитанного, один раз при двух тиках, дайджест раз в день, отписка по токену (неверная подпись → 400), шифрование пароля, `unavailable` без настроек.

### iframe
- `<iframe src="url" sandbox="allow-scripts allow-forms allow-same-origin" referrerpolicy="no-referrer">` (Q2): `allow-same-origin` безопасен только потому, что хост плагина ≠ хост приложения (`checkPluginUrl` при регистрации и перед показом). Без `allow-popups`, `allow-top-navigation`.
- Cookie `planar_sid` — без атрибута `Domain` (host-only); проверяется тестом (заголовок `Set-Cookie` входа).
- CSP: до первого iframe плагина web добавляет в `<head>` `<meta http-equiv="Content-Security-Policy" content="frame-src <origin включённых плагинов через пробел>">` (нет плагинов — `frame-src 'none'`). Политика только сужается: плагин, добавленный после загрузки страницы, показывается после перезагрузки (подсказка «Перезагрузите страницу»).
- Плагин не получает cookie, токенов и данных сверх ответов протокола.

### Протокол postMessage v1
Все сообщения — объекты с `planar: 1` и `type`. Хост отправляет только `iframe.contentWindow.postMessage(msg, plugin.origin)`. Хост принимает сообщение только если `event.source === iframe.contentWindow`, `event.origin === plugin.origin`, `data.planar === 1` и `type` известен; иначе молча игнорирует (без ответа, `console.warn`).

| type | направление | поля | ответ |
|---|---|---|---|
| `ready` | плагин → хост | — | `init` |
| `init` | хост → плагин | `plugin: {id}`, `user: {id, name, login, role}`, `context: {point: 'taskPanel', taskId, projectId, spaceId} \| {point: 'page'}`, `permissions`, `locale: 'ru'\|'en'`, `theme: 'light'\|'dark'` | — |
| `query` | плагин → хост | `id: string`, `entity: PluginEntity`, `where?: {<поле>: значение}`, `ids?: uuid[]`, `limit?: int ≤ 500` | `result` с `rows` |
| `mutate` | плагин → хост | `id`, `name`, `args` | `result` |
| `navigate` | плагин → хост | `path` | — |
| `resize` | плагин → хост | `height: int` | — |
| `result` | хост → плагин | `id`, `ok: true, rows?` или `ok: false, error: {code, message}` | — |

- `query`: `entity` ∉ `permissions.read` → `forbidden`; `where` — только `id` и поля `indexes` сущности (C-schema), иначе `invalid_request`; данные — из локальной реплики (то, что видит пользователь); `users` — только `{id, name, login, avatarFile}`; `limit` по умолчанию 100.
- `mutate`: мутатор не из разрешённых по `permissions.write` → `forbidden` без запроса; иначе `POST /api/plugins/:id/mutate {name, args}` (сессия; Bearer → 403): сервер проверяет, что плагин есть, `enabled` и мутатор разрешён (иначе `403 forbidden`), и выполняет `executeMutations` от пользователя сессии (его права тоже действуют; ошибки мутатора — по C-http). Результат приходит синхронизацией.
- `navigate`: `path` начинается с `/`, не с `//` и не с `/\` → `router.push`; иначе игнор.
- `resize`: `height` ограничивается 40–2000 px (только `taskPanel`).
- Смена задачи — новый iframe (ключ — `taskId`).
- Web: `taskPanels` `plugins:panel` «Плагины» — iframe каждого включённого плагина с `taskPanel`; `nav` `plugins:pages` — ссылки на `/m/plugins/p/:pluginId` для плагинов с `page`; `settings` `plugins:admin` (`adminOnly`) — регистрация, права, точки, включение.
- Пример — `examples/plugin-hello/index.html` (статическая страница без сборки): по `init` показывает пользователя и название задачи (`query tasks`), кнопка «Комментарий» (`mutate comment.create`).
- Приёмка: тесты моста — чужой `origin`, чужой `source`, `planar ≠ 1` → игнор; `query` вне `read` и `mutate` вне `write` → `forbidden`; сервер — `403` на мутатор вне прав, выключенный плагин, Bearer; `checkPluginUrl` — origin приложения, `javascript:`, userinfo, `http:` не localhost.
