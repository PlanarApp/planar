# WK-16 — бюджеты §7: A/B main против feature/work

## Метод
- A = `main` (ed85156, фаза 1), B = `feature/work` (7e65fad, фаза 2). `bash e2e/web/perf/run.sh` (reset, seed 10 000 задач, прод-сборка, vite preview, Chromium headless), 5 прогонов каждой фазы, строго чередуя A1 B1 A2 B2 … на одном хосте, под `lock cpu`.
- В A подложен `measure.spec.ts` из B (селектор строки после WK-8; в main старый) — иначе фазы мерили бы разным инструментом. Приложение в A не менялось.
- Каждый прогон: cold — медиана 3, warm — медиана 5, mutate — p95 из 20, switch — p95 из 10, realtime — p95 из 10. Показатель фазы — медиана 5 прогонов. Сырьё — `build/artifacts/WK-16/ab.tsv`, логи — `runs/`.
- «Шум»: перестановочный критерий (все C(10,5) разбиений), односторонний p(B хуже A).

## Вывод
Ни один показатель не ухудшился за пределами шума (при n=5 на фазу p ≥ 0,12 везде; различимы были бы сдвиги порядка 15–20 %). Cold, warm, mutate, scroll — равны. Причина ухудшения не найдена, потому что ухудшения не подтверждено; профиль и патч не делались.

Наблюдения у порога (WK-8):
- switch: B +8 % номинально, диапазоны перекрываются (A 90,0…100,2; B 89,8…106,9); 3 из 5 прогонов B выше 100, у A — 1 из 5 (100,2). Это тот же класс «у порога», что в фазе 1 (WB-17: 90…111), не регрессия, но запаса нет ни у A, ни у B.
- realtime p95: по 10 правкам p95 = максимум; у B один выброс 692 (прогон B1), остальные 323…583; у A 326…446. Выбросы — серверная часть (push), как в WB-17 (296…956); медиана 201 против 204.
- warm: 397 у B против бюджета 400 — запас 0,7 %; у A 425 (выше бюджета в 3 из 5 прогонов). B не хуже, но бюджет держит впритык.

## Что добавилось в фазе 2 на горячих путях (гипотеза, не замерено)
Читал `git diff main feature/work -- apps/web`: на пути старта/перехода/реалтайма добавлено — `import.meta.glob` манифестов модулей и регистрация сущностей (`sync/index.ts`), версия Dexie 3 + динамическая `schemaVersion` (читает localStorage один раз при создании БД), поиск в `moduleEntities` на каждый `check`/`scan` в `DexieTx` (Map.get — пренебрежимо), `ModuleScreen`/реестр модулей. Профиль не снимался, поскольку ухудшение не выявлено; если switch >100 окажется стабильным при большем n, начать с CPU-профиля по методике WB-17 (`e2e/web/perf/profile/`) на переходе проекта.

## Допущения и границы
- Один хост, shared с другими работами (24 ядра, load ~3); чередование ABAB уменьшает дрейф, но не убирает его.
- n=5: мощность низкая, детектируется только крупный сдвиг; для решения о switch/realtime нужно ≥ 15 прогонов на фазу.
- Сид без данных модулей (время, спринты): нагрузка модулей на bootstrap не проверялась — только их фиксированная стоимость в клиенте.
- Начальный JS ≤ 200 КБ (план work §1) не мерился — вне задачи.
