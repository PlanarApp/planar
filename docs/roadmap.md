# Роадмап Planar

Трекер задач уровня ClickUp, но быстрее и проще. Один workspace. Интерфейс мгновенный за счёт локальной реплики данных, как в Linear.

## 1. Решения пользователя (2026-10-22)

- **Функции:** разбивка MVP / v1 / v2 / ✗ из обсуждения принята.
- **Фронтенд:** Vue 3 + Vite, SPA, ставится как PWA. Мобильная версия — тот же PWA с отдельными раскладками.
- **Синхронизация:** вариант B — своя лёгкая, как в Linear: локальная реплика, оптимистичные мутации, журнал изменений `changes`, WebSocket-«пинок».
- **БД:** PostgreSQL 18 закрывает всё — кэш, очереди, pub/sub (LISTEN/NOTIFY), векторный поиск (pgvector, заготовка на будущее). Redis не используем.
- **ORM:** Drizzle.
- **Авторизация:** пока только логин и пароль.
- **Workspace:** один. Сущности workspace в БД нет, инстанс и есть workspace.
- **SSO, LDAP, 152-ФЗ:** не нужны.
- **Локальный запуск:** скрипт поднимает весь стек в docker compose с первого дня.
- **Срок:** уложиться в 24 часа параллельной работы.
- **Название:** Planar.
- **Интеграции (2026-10-22):** пользователь сам выпускает API-токен; встроенный MCP-сервер, чтобы ИИ-агенты и внешние системы работали с задачами. Входит в ярус A.
- **Старт:** до 8 исполнителей одновременно; на шлюзах проверяет пользователь, в `main` сливаем только с его одобрения.

## 3. Архитектура в одном абзаце

Мутации — именованные функции из `packages/shared/mutators`. Одна и та же функция выполняется дважды: на клиенте оптимистично над Dexie и на сервере в транзакции Drizzle, через общий интерфейс `Tx {get, put, del, scan}`. Сервер дополнительно проверяет права. Каждая запись на сервере добавляет строку в `changes(seq bigserial, space_id, entity, id, op, data)` и делает `NOTIFY`. Шлюз рассылает подключённым клиентам `poke{seq}`, клиент делает `pull?cursor=` и получает только изменения из своих пространств. Неподтверждённые мутации лежат в очереди в IndexedDB. После pull клиент берёт состояние сервера и заново применяет поверх него неподтверждённые мутации (rebase, как в Replicache). Так офлайн-режим получается почти бесплатно. Конфликты решаются по правилу last-write-wins на уровне поля, источник истины — сервер.

## 4. Контракты (пишутся до первого исполнителя, `docs/contracts/core.md`)

| ID | Стык | Владелец → потребители |
|---|---|---|
| C-schema | Таблицы, поля, индексы, инварианты (users, sessions, spaces, space_members, projects, statuses, tasks, task_assignees, labels, task_labels, checklist_items, comments, attachments, activity, notifications, push_subscriptions, saved_views, settings, changes) | core → все |
| C-sync | `GET /sync/bootstrap`, `GET /sync/pull?cursor`, `POST /sync/push {clientId, mutations:[{id,name,args}]}`, WS `/ws`: `poke`, `hello`. Коды ошибок, повторы, идемпотентность по `mutation.id` | core → web |
| C-mutators | Интерфейс `Tx`, реестр `name → {args: zod, run(tx,args,ctx)}`, серверный хук прав | shared → core, web |

| C-ui | Дизайн-токены (цвета, отступы, тёмная тема), базовые компоненты, брейкпоинты desktop и mobile | web → features |

## 7. Приёмка и бюджеты скорости (проверяются в CR-9, числами)

- **Бандл:** начальный JS ≤ 200 КБ в gzip. Модули и виды грузятся отдельными чанками.
- **Старт:** холодный bootstrap на 10 000 задач до интерактива ≤ 2 с. Тёплый старт из IndexedDB ≤ 400 мс.
- **Отклик:** локальная мутация до перерисовки ≤ 50 мс. Переход между проектами и видами ≤ 100 мс, без сетевого ожидания.
- **Реалтайм:** правка в одном клиенте появляется в другом ≤ 500 мс (локальный стек).
- **Офлайн:** правки без сети сохраняются в очереди и доходят до сервера после переподключения, ни одна не теряется (e2e-тест).
- **Права:** пользователь не получает данные приватного пространства ни через pull, ни через WS, ни через файлы (e2e-тест).
- **Запуск:** `./dev.sh up && ./dev.sh seed` на чистой машине поднимает рабочий стек.

## 8. Условия остановки (шлюзы к пользователю)

- Сдвиг критического пути больше чем на 2 ч, или бюджет из §7 не выполняется после 2 попыток.
- Изменение контракта C-sync или C-mutators после старта волны 2.
- Любая новая зависимость вне §2.
- Шлюз MVP и шлюз v1: проверка пользователем и слияние в `main`.

## 9. Порядок модулей
- `core` стартует первым: координатор пишет контракты §4, затем CR-1.
- `web` создаётся от `feature/core` после слияния CR-1 и контрактов. Свежий core координатор web берёт слиянием `feature/core` в свою ветку, в `main` ничего не вливается.
- `features` создаётся от `main` после шлюза MVP.
