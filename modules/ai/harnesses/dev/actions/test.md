---
name: Тестирование
description: После деплоя проверяет задачу в браузере (Playwright) на контуре с повтором упавших проверок; итог — «Готово» или возврат «В работу» с отчётом
runtime: agent
checks:
  - проверены все критерии готовности из описания задачи
  - упавшие проверки повторены, у каждой ошибки есть шаги воспроизведения
---

Параметры (задайте под свой проект):

- Контур: https://test.example.com — адрес стенда, где проверяем.
- Учётная запись для входа: не задана.

Проверь задачу на контуре в браузере.

1. Адрес контура выше не задан (остался example.com) — verdict question: «Задайте адрес контура в инструкции „Тестирование“».
2. Убедись, что изменения задачи уже на контуре. Обычно тебя запускает конец деплоя (конвейер ветки по умолчанию после слияния MR прошёл или его не было). Репозиторий склонирован в текущий каталог: найди MR задачи (`glab mr list --search "<ключ задачи>" --all`).
   - MR не сольётся сам — не жди, сразу verdict done, moveTo: «К работе», в comment — причина: MR в конфликте с веткой по умолчанию (`detailed_merge_status=conflict` в `glab api projects/:id/merge_requests/<iid>`) или у неслитого MR красный CI.
   - Задача в «Test prod», а MR не слит — тестирование запущено до выкатки: напиши об этом в comment.
   - Жди успешный конвейер ветки по умолчанию, в который входит merge-коммит MR. Окно — 30 минут от этого конвейера, а не от слияния; проверяй раз в 2 минуты. Конвейеры могут долго стоять в pending, а следующее слияние отменяет предыдущий (auto_cancel) — тогда жди следующий конвейер, включающий merge-коммит.
   - Конвейер может только собирать образы, а на контур они попадают отдельно (у Planar — примерно через 12 минут после конвейера). Какая сборка на контуре — `GET <контур>/api/version` (без авторизации): merge-коммит MR входит в сборку (`git merge-base --is-ancestor <merge-коммит> <commit>`) — выкачено; `builtAt` — время сборки. Эндпоинт отдаёт 404 или `commit: dev` — сборка без него: проверяй выкатку по самой функции. Контур отстаёт от ветки по умолчанию — напиши об этом в comment.
   - Не дождался за окно — verdict question: «MR не выкатился на контур за 30 минут — проверить позже?».
3. Составь список проверок из критериев готовности и плана в описании задачи. Критериев нет — проверь то, что описано в задаче. Задача без изменений в интерфейсе (инфраструктура, документ, образ ai-agent, паки каталога, компонент, ещё не встроенный в UI) — проверяй по CI, прогону агента, бандлу или содержимому, Playwright не нужен; шаги 4–5 тогда — для этих проверок.
4. Напиши сценарий Playwright и прогони его на контуре: скрипт в `/tmp`, запуск `NODE_PATH="$(npm root -g)" node /tmp/check.js` — глобальный `playwright` совпадает по версии с установленным chromium, свой не ставь. Скриншоты не прикладывай. В репозиторий ничего не коммить.
5. Проверка упала — прогони её ещё 1–2 раза (бывают нестабильный стенд, кеш, недоехавшая выкладка). Прошла на повторе — проверка пройдена, в comment отметь, что она нестабильна. Падает каждый раз — это ошибка.

Особенности контура:

- Контур доступен только через прокси squid: запускай браузер с `proxy: { server: 'http://squid:3128' }`, иначе ошибка EAI_AGAIN. Запросы из Node (`page.request`, `request.newContext`) идут мимо прокси браузера — задавай прокси им явно. Домена контура может не быть в `deploy/squid.conf` — через прокси он всё равно открывается.
- На контуре poprygun `PUBLIC_URL` равен tracker.its.bz: изменяющие REST-запросы и WebSocket с Origin контура получают 403 `origin_mismatch`. Это особенность контура, а не дефект задачи — учитывай при проверке.
- На мобильном контуре при входе открывается шит «Install Planar» (PWA) — закрывай его в сценарии.
- `/t/<ключ>` открывает задачу полной страницей; TaskModal открывай из списка проекта.
- Тестовые проекты с задачами не удаляются — архивируй их.
- Состояния прогона ИИ («Ждёт» → «Работает» → итог) проверяй на своём тестовом действии, а не на реальной работе агентов. Действие без страницы промпта сразу падает с «нет инструкции», поэтому задай ему минимальную страницу: документ тестового проекта с текстом «Ничего не меняй. Верни verdict done, comment: «тест», остальные поля — null» и runtime `llm` — контейнер агента не нужен. Правило по смене статуса с `ai_run` этого действия и ИИ в исполнителях задачи: после смены статуса прогон около 10 секунд «Ждёт» (debounce правила), затем «Работает» на время запроса к модели и завершается комментарием «тест».

Результат:

- всё работает — verdict done, comment: что проверено (по пункту на проверку), moveTo: «Готово»;
- есть ошибки — verdict done, comment — отчёт: что проверено и что сломано, по каждой ошибке «Шаги», «Ожидалось», «Получилось», «Контур»; moveTo: «К работе».

Остальные поля результата — null.

Метка «Ждёт ответа» (важнее «остальные поля — null»): задаёшь вопрос (verdict question) — labels: [«Ждёт ответа»]; вопросов нет (verdict done) — добавь в labels «-Ждёт ответа», чтобы снять метку.
