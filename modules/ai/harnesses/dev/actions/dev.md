---

Реализуй задачу в репозитории проекта (он склонирован в текущий каталог). Если репозитория нет — verdict fail: «в проекте нет подключения GitLab».

1. Прочитай описание задачи, план в нём и комментарии (файл контекста). Прочитай README и инструкции для агентов в репозитории (AGENTS.md, CLAUDE.md, CONTRIBUTING.md) и следуй им: как запускать тесты, линтер, как называть коммиты.
2. Чего-то не хватает для работы или требования противоречат коду — verdict question, по одному вопросу на пункт. Ничего не пушь.
3. Создай ветку `mr/<ключ задачи>` от ветки по умолчанию (ключ — из контекста, например `mr/PLN-12`). Ключ в ветке и заголовке MR связывает MR с задачей.
4. Сделай минимальное изменение, которое полностью решает задачу. Добавь или обнови тесты, если в проекте они есть.
5. Прогони тесты и линтер проекта. Красные — исправь. Не удаётся за разумное время — verdict fail с выводом ошибок в comment, ничего не пушь.
6. Закоммить только свои файлы, сообщение — `<ключ задачи>: <суть>`. Запушь ветку: `git push -u origin mr/<ключ>`.
7. Открой MR в ветку по умолчанию: `glab mr create --source-branch mr/<ключ> --title "<ключ>: <суть>" --description "<что сделано и как проверено>" --yes`. В описание MR не пиши ключи чужих задач.
8. Включи автомерж после успешного CI: дождись у MR конвейера (`glab api projects/:id/merge_requests/<iid>` → поле `head_pipeline` не null, проверяй раз в 15 с до 5 минут), затем `glab api -X PUT projects/:id/merge_requests/<iid>/merge -f merge_when_pipeline_succeeds=true`. Проверь, что MR остался открытым. Не используй `glab mr merge` — он сливает сразу. Конвейера нет за 5 минут — оставь MR без автомержа и напиши об этом в comment.

Результат — verdict done:

- comment: ссылка на MR, что сделано, как проверено (какие тесты и линтер прошли);
- descriptionAppend: коротко — что изменено и где;
- moveTo: «Test prod».

Остальные поля результата — null.
