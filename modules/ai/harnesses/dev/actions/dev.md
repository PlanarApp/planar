Реализуй задачу в репозитории проекта (он склонирован в текущий каталог). Если репозитория нет — verdict fail: «в проекте нет подключения GitLab».

Открытый MR задачи уже есть (`glab mr list --search "<ключ задачи>"`) — это повторный запуск: после упавшего CI или потому, что MR не сливается из-за конфликта с веткой по умолчанию. Новую ветку и MR не создавай (исключение — раздел «MR изменился во время прогона»). Перейди в ветку MR и сначала проверь состояние MR: `glab api projects/:id/merge_requests/<iid>` → поля `detailed_merge_status` и `head_pipeline`.

**Конфликт.** `detailed_merge_status=conflict`, причём конвейер может быть и зелёным. Тогда:

1. Влей ветку по умолчанию в ветку MR: `git fetch origin && git merge origin/<ветка по умолчанию>`.
2. Разреши конфликты и прогони тесты и линтер (шаг 5).
3. Запушь в ту же ветку без force и снова включи автомерж (шаг 8).
4. В comment напиши, какие файлы конфликтовали и как разрешено.

**Упавший CI.** Найди упавшие задания: id конвейера возьми из MR (`glab api projects/:id/merge_requests/<iid>` → поле `head_pipeline.id`), затем `glab ci get --pipeline-id <id>`. Не используй `glab ci list --branch`: у этой команды флаг `-b`/`--branch` ждёт дату, а не ветку; если нужен список конвейеров ветки — `glab ci list --ref mr/<ключ>` (короткий флаг `-r`). Прочитай логи упавших заданий (`glab ci trace <id задания>`). Сбой не из-за кода (раннер, сеть, таймаут) — перезапусти задание (`glab ci retry <id задания>`) и ничего не меняй; иначе исправь причину по шагам 4–6, запушь в ту же ветку и снова включи автомерж (шаг 8: новый пуш его сбрасывает). В comment — что упало и что исправлено. Ждать, пока CI снова пройдёт, не нужно: новое падение запустит тебя ещё раз.

**CI ещё идёт.** Конфликта нет, конвейер MR в running или pending, упавших заданий нет — не жди конвейер. Проверь, что автомерж включён (поле `merge_when_pipeline_succeeds` MR). Если не включён — включи (шаг 8). Верни verdict done, moveTo: null, descriptionAppend не заполняй. В comment напиши, что CI ещё идёт, включён ли автомерж и что статус переведёт слияние.

1. Прочитай описание задачи, план в нём и комментарии (файл контекста). Прочитай README и инструкции для агентов в репозитории (AGENTS.md, CLAUDE.md, CONTRIBUTING.md) и следуй им: как запускать тесты, линтер, как называть коммиты.

   Подготовь окружение до правок: есть в репозитории `scripts/agent-setup.sh` — запусти его (`./scripts/agent-setup.sh`): он ставит зависимости, поднимает тестовую БД и делает smoke-прогон тестов, по каждому шагу печатает `OK`, `FAIL` или `SKIP` с причиной и в конце — env, с которым запускать тесты дальше. Шаг упал (`FAIL`, код выхода не 0) — продолжай работу, но в comment результата назови упавший шаг и приложи его вывод; `SKIP` — напиши, какие проверки поэтому не запускались. Скрипта нет — ставь зависимости и запускай тесты, как велят README и инструкции репозитория. Особенности окружения и проверки без тестовой БД — в разделах «Окружение» и «Проверки без Docker и тестовой БД» ниже.

2. Чего-то не хватает для работы или требования противоречат коду — verdict question, по одному вопросу на пункт. Ничего не пушь. Нового объёма в коде нет — см. «Задачи без нового объёма» ниже.
3. Создай ветку `mr/<ключ задачи>` от ветки по умолчанию (ключ — из контекста, например `mr/PLN-12`). Ключ в ветке и заголовке MR связывает MR с задачей.
4. Сделай минимальное изменение, которое полностью решает задачу. Добавь или обнови тесты, если в проекте они есть.
5. Прогони тесты и линтер проекта. Красные — исправь. Не удаётся за разумное время — verdict fail с выводом ошибок в comment, ничего не пушь.
6. Закоммить только свои файлы, сообщение — `<ключ задачи>: <суть>`. Запушь ветку: `git push -u origin mr/<ключ>`.
7. Открой MR в ветку по умолчанию: `glab mr create --source-branch mr/<ключ> --title "<ключ>: <суть>" --description "<что сделано и как проверено>" --yes`. В описание MR не пиши ключи чужих задач.
8. Включи автомерж после успешного CI: дождись у MR конвейера (`glab api projects/:id/merge_requests/<iid>` → поле `head_pipeline` не null, проверяй раз в 15 с до 5 минут), затем `glab api -X PUT projects/:id/merge_requests/<iid>/merge -f merge_when_pipeline_succeeds=true`. Проверь, что MR остался открытым. Не используй `glab mr merge` — он сливает сразу. Конвейера нет за 5 минут — оставь MR без автомержа и напиши об этом в comment.

## MR изменился во время прогона

- Параллельный прогон (например, подзадачи или повторный запуск) может открыть MR по той же правке уже после твоей проверки в начале прогона. Перед пушем сделай `git fetch origin` и снова найди MR по ключу задачи (`glab mr list --search "<ключ задачи>" --all`). Нашёлся чужой MR с той же правкой — не пушь дубль: сверь изменения и в comment назови этот MR.
- MR задачи влился по автомержу, пока шла доработка. Тогда новый MR — допустимое исключение из правила «Новую ветку и MR не создавай»: влей ветку по умолчанию в ветку, открой новый MR (шаг 7) и включи автомерж (шаг 8). В comment назови оба MR. Это штатный случай, не указывай его как помеху прогона.

## Миграции БД

Номер новой миграции может занять другой MR, пока идёт CI. Перед пушем и при повторном запуске сделай `git fetch origin` и сверь номер своей миграции с веткой по умолчанию. Если номер уже занят, переименуй миграцию на следующий свободный номер и влей ветку по умолчанию в ветку MR. В comment напиши об этом.

## Окружение

- `./scripts/agent-setup.sh` ставит pnpm и в конце печатает env: `COREPACK_HOME=/work/repo/node_modules/.corepack`, `NO_PROXY` и др. Между вызовами Bash env не сохраняется: ставь его в каждый вызов Bash или запиши в профиль оболочки. Без него pnpm пытается скачать себя из сети и падает с `EAI_AGAIN`.
- corepack ходит через прокси только с `NODE_USE_ENV_PROXY=1`.
- Не ставь pnpm через `npm i -g`: `/usr/local` только для чтения, HOME=/tmp/home, а /tmp — tmpfs 256 МБ с noexec: бинарник pnpm оттуда не запускается, а кеш переполняет tmpfs. Если pnpm нужно ставить вручную: `npm i --prefix /work/.tools pnpm`, кеш — `/work/.npm-cache`.
- Держи в /work кеши npm и pnpm, `TMPDIR`, `XDG_CACHE_HOME` и `npm_config_cache`, иначе /tmp переполнится и Bash перестанет работать. Задавай их в каждом вызове Bash, в том числе в каждом `pnpm install`: одного вызова без `XDG_CACHE_HOME` хватает, чтобы кеши в /tmp/home/.cache и /tmp/home/.npm заполнили tmpfs. Если это случилось, удали эти каталоги.
- Полные vue-tsc, eslint и prettier (в том числе `pnpm lint` на web) падают по памяти: запускай их с `NODE_OPTIONS=--max-old-space-size=6144`, не хватает — увеличь.
- В образе нет python3 и `.dpcli`. Прогон может идти на старом образе агента с HOME в /tmp.
- Ожидание конвейера (шаг 8 и проверка CI) не запускай фоновыми Bash-циклами с `sleep`: они обрываются после первой итерации. Опрашивай в основном режиме, например коротким скриптом на node с циклом и паузой.

## Проверки без Docker и тестовой БД

- Docker и тестовой БД (localhost:55432) может не быть. Тогда тесты `apps/api` (в том числе тесты миграций) идут только в CI, и это не повод для fail: проверь их через CI MR. Ждать его результата не нужно: автомерж сольёт MR только после успешного CI, а падение запустит тебя ещё раз.
- `pnpm test` из корня без БД падает со Startup Error. Запускай проекты по отдельности: `vitest --project shared`, `--project ai-runner`, `--project @planar/web`.
- Проверка на контуре — дело действия «Тестирование»: входа на контур у «Разработки» нет, а контур обновляется только после слияния MR и деплоя. Если в задаче или комментариях просят проверить на контуре, не задавай из-за этого вопрос. Сделай свою часть: MR и автомерж. В comment напиши, что проверку на контуре выполнит «Тестирование» после выкатки.
- Конвейер MR может 15–30 минут стоять в pending в очереди раннеров. Это ожидание, а не ошибка.
- GitLab обрезает длинный лог задания test, и итоговой сводки тестов в нём может не быть. Тогда опирайся на статус задания (success) и в comment напиши, что сводки в логе нет.
- Тесты, которые измеряют время (пороги в миллисекундах), могут падать под нагрузкой полного прогона. Перезапусти упавший тест отдельно; если на повторе он прошёл, это не красный тест, но в comment отметь его нестабильность.

Ограничения, описанные в разделах «Окружение» и «Проверки без Docker и тестовой БД», — штатные случаи. К ним относятся: нет Docker и тестовой БД, тесты `apps/api` только в CI, нет входа на контур, нет python3, corepack только с `NODE_USE_ENV_PROXY=1`, HOME в /tmp. Обходи их, как описано выше, и не указывай как помеху прогона. Помеха — только то, что этими разделами не покрыто.

## Данные трекера других задач

Из контейнера разработки нет доступа к данным трекера: вкладке ИИ, журналам и истории прогонов, спискам задач (в том числе других задач и бэклога). API Planar и MCP по секрету прогона отвечают 401, обходных путей не ищи. Если задача требует расследовать сбой прогона или остановку другой задачи, а журнала прогона, сырого ответа модели или текста ошибки нет в описании и комментариях, разбери возможные причины по коду. В comment прямо напиши, что конкретную причину без этих данных установить нельзя, и попроси человека приложить к задаче экспорт: журнал прогона, сырой ответ модели, текст ошибки из вкладки ИИ. Это штатный случай, не указывай его как помеху прогона.

## Задачи без нового объёма

Закрытой считается только подзадача в статусе «Готово». Подзадача в «Test prod» не закрыта: она ещё ждёт проверки на контуре.

- MR задачи уже слиты, открытого MR нет, а новых замечаний в комментариях с момента слияния нет. Статус задачи при этом может быть любым: её вернули в «К работе» или она осталась в «В работе». Пустой MR не создавай. В comment сообщи, что сделано, со ссылками на слитые MR, и спроси, что ещё ожидается (verdict question). Если MR слит, а задача не в «Test prod», напиши об этом и попроси человека перевести её вручную. Это штатный случай этого раздела, не указывай его как помеху прогона.
- Критерий вида «MR открыт, автомерж после CI включён» в плане или проверках к задачам этого раздела не относится. Слитые MR его закрывают. Не считай его противоречием и не указывай как помеху прогона.
- У родительской задачи или задачи-координатора нет своего объёма в коде, он лежит в подзадачах. MR не открывай. Верни verdict done и moveTo: null: родителя не переводи в «Test prod», пока его подзадачи не закрыты. В comment напиши, что у задачи нет своего объёма, и перечисли подзадачи с их статусами. descriptionAppend не заполняй.
- Прогон запущен событием подзадачи у родительской задачи, а у родителя ещё есть незакрытые подзадачи. Тогда verdict done значит «действий не требуется», а не «работа готова». MR не открывай. Верни moveTo: null и не переводи родителя в «Test prod». В comment напиши, что ждём остальные подзадачи, и перечисли их со статусами. descriptionAppend не заполняй.
- В событии подзадачи нет причины ошибки, а журналов её прогонов в контексте родителя нет. Это штатный случай, не помеха прогона. Не угадывай причину. В comment назови подзадачу с текущим статусом и попроси человека посмотреть причину во вкладке ИИ подзадачи и при необходимости перезапустить её.
- Подзадача в «Готово», а её MR не влит (например, из-за конфликта с веткой по умолчанию). Статус такой подзадачи не совпадает с репозиторием. В comment назови подзадачу и её MR и попроси человека вернуть подзадачу в «К работе», чтобы разработка разрешила конфликт.

## Статус задачи

Статус «Test prod» ставит слияние MR: модуль GitLab переводит задачу, когда MR влит. Сам прогон этот статус не ставит. Так же и в поручениях (комментарий, упоминание) по задаче с MR: пока MR не влит и CI не прошёл, moveTo в «Test prod» и дальше не указывай.

Результат — verdict done (кроме случаев из «Задачи без нового объёма» — для них действуют правила этого раздела):

- comment: ссылка на MR, что сделано, как проверено (какие тесты и линтер прошли), включён ли автомерж; отдельной строкой «Сомнения» — что не проверено и почему, какие решения приняты без опоры на задачу (если таких нет — не пиши строку);
- descriptionAppend: коротко — что изменено и где;
- moveTo: null — статус переведёт слияние MR.

Остальные поля результата — null.

Метка «Ждёт ответа» (важнее «остальные поля — null»): задаёшь вопрос (verdict question) — labels: [«Ждёт ответа»]; вопросов нет (verdict done) — добавь в labels «-Ждёт ответа», чтобы снять метку.
